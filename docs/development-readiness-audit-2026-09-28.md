## 3. 需要在对应开发范围内闭合的问题

优先级的含义：P1 为对应核心模块定型／交付前必须解决；P2 为对应功能实现、联调或交接前补齐。不是将所有条目都列为全项目停工条件。

### A-01 / P1：暂停语义完整，实际控制路径尚未闭合

**证据**：[技术设计 §4](technical-design.md#4-控制权暂停与恢复)已提出控制代次、用途许可、停止确认及本机离线意愿，但本机意愿进入动作许可的方式仍是候选。[证据盘点](verification-readiness.md#首期控制能力增量复核2026-09-28)记录的代码缺口仍可复查，本轮九个文件指纹一致，并抽读了关键分支：

- `socialgrowth_supervision.py:96` 的读取动作在取得会话后提前返回；`supervision.ts:223` 的 read 分支也提前允许。
- `runtime.ts:164` 的 `holdDevice` 在 running／checking 时拒绝接管，不能直接作为“运行中也必须受理”的提供者暂停。
- `task_manager.py:549` 的非 Windows 分支发送 SIGTERM，随后写 cancelled；该结果本身不证明动作和在途调用已结束。
- 状态补图、手动截图和协助取图也属于真实手机访问，不能只修 Artemis 常规动作入口。

**影响**：照现有 Demo 拼接 App 按钮，会出现“已受理但仍可读屏”“显示停止却尚有操作”“旧恢复覆盖本机暂停”等风险。这是当前适配边界，不能反过来修改已确认业务语义。

**最小闭合产物**：明确真实动作与读取许可的统一检查点、许可失效规则、本机意愿同步、在途动作记录、停止证据与控制交还条件；给出中心／App／执行进程的交错时序。优先验证运行中暂停、离线暂停后重连、恢复中再次暂停、退出后旧恢复到达，以及状态页截图旁路。不能证明停止时继续保留未知，而非用超时判停。

**时点与责任**：执行与客户端技术工作先做，控制模块定型和交付前闭合；不阻塞独立页面、数据模型或受控探索。

### A-02 / P1：首次接入路径仍缺目标环境证据

**证据**：[网络研究的首轮连接路径](research/vpn-mdns-device-connectivity.md#首轮连接路径收敛2026-09-28)明确 V-02～V-05 未验证，首次配对凭据通路也尚未落实。[推进安排](next-stage-plan.md#按交付时点落实的条件)要求接入定型前先做增量可行性验证。

**影响**：不能从“既有手机可以远程执行”推出“新手机在无现场电脑条件下可以完成中心首次配对”，也不能从本地 NSD 发现推出中心可连接正确手机。若后期才发现不成立，会返工接入引导、身份关联及网络方案。

**最小闭合产物**：候选机型／系统／ADB／Tailscale 版本、既有连接接法、实际中心与出口拓扑、首次配对凭据的受控短期通路，以及启用出口后的端点发现、实际连接、FB/YT 上网和故障恢复记录。支持清单只列有依据的范围，其他环境明确不支持或未验证。

本轮复查官方资料仍支持文档的谨慎结论：标准无线 ADB 流程包含工作站配对，ADB 信任对应主机密钥；Android 每用户／资料仅一个活动 VPN 服务；Tailscale 使用出口时默认限制本地网络访问。它们均不能代替本项目目标网络实测。[Android ADB](https://developer.android.com/tools/adb#connect-to-a-device-over-wi-fi)、[AOSP 配对机制](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)、[Android VPN](https://developer.android.com/develop/connectivity/vpn)、[Tailscale 出口本地访问](https://tailscale.com/docs/features/exit-nodes#local-network-access)。

**时点与责任**：网络、Android、执行技术工作；资源落实后先验证，接入实现定型前闭合。无需用户凭偏好判断技术是否可行。

**证据**：[技术设计开头及 §1～3](technical-design.md)明确为 0.1 建议、R-134～141 增补未整体架构重审；数据表、API 路径可在实现时细化，Web 框架、模型和组件尚未锁定。已有对象分组及最小控制契约有价值，不能说“完全没有设计”。

**最小闭合产物**：按首个交付范围确定采用的架构建议及版本，形成核心实体关系、字段含义、唯一性／版本检查、事务边界和接口请求／响应／冲突结果。重点落在设备关联、控制请求、尝试和回执、内容平台名额及资源交接；用少量具体时序覆盖重复、迟到、撤权和重启。

还需落实 R-075 已明确留下的“单次恢复如何计数、耗时从何时累计、人工处理后何时形成新一轮”；不能在换进程、换会话或换错误类型时无条件重置 2 次／5 分钟预算。见[原确认 R-075](requirements-alignment.md#r-075自动恢复采用累计-2-次5-分钟的可配置初始限额)。

**时点与责任**：技术实施负责人在对应模块编码与联调过程中形成可审查基线。无需另造通用规则引擎、消息平台、全量 ADR 或先写完全部 API；但不能由多个端各自解释状态含义。

### A-05 / P2：新接入阶段“无项目事项”的运营归属需要补上

**证据**：[App 规格](android-app-page-spec.md#条件检查谁能处理检查了什么结果何时有效)允许网络节点／出口待运营配置、本机检查后等待首次分配；此时手机尚无项目。[业务流程的人工介入路径](business-workflow.md#从人工介入回到自动执行)却以项目、任务和项目负责人路由为主。原邀请运营仅在账号找回中被明确为联系起点。

**缺口**：首次配对、网络配置或设备关联冲突发生在分配前时，在哪个运营列表出现、谁接收／负责、如何与提供者“等待运营”保持同一事项，当前没有完整衔接规则。

**建议**：复用全局“提供者／账号与设备”及待办入口，允许未分配项目的接入事项，记录实际责任人和处理人；由邀请运营作为初始联系人的方案可集中确认。保留运营同权，不新增管理员角色或工单系统；不能强行填一个虚假项目来满足通知模型。

**时点与责任**：产品与工程在首条跨端接入联调前补一条完整路径；这项不能等到已有项目任务验收时才发现。

### A-06 / P2：平台与反馈能力需要落实到首条真实闭环

**证据**：[平台研究](research/platform-and-android-feasibility.md)、[数据时间粒度研究](research/effect-data-time-granularity.md)说明多个入口、FB 指标粒度及实际权限尚未核验；[技术设计 §7](technical-design.md#7-业务-ai-与反馈的最小实现)仍未定业务模型和具体采集来源。旧短链入口不能证明已有真实跳转统计服务。

**最小闭合产物**：先为获准的第一条纵向流程列清实际平台／形式、文件输入约束、正确身份与内容的核验证据、有效引流路径、指标来源／权限／时间粒度，以及业务 AI 的有限输入输出与系统校验。保留结构相同的首期完整覆盖表，随后覆盖 FB 视频／图文、YT 两种视频和短剧；不把一次 MP4 准备通过外推到图文。

**影响**：只有发布与页面建设，真实反馈无来源，仍无法完成 R-063／R-064 要求的闭环；模型输出一份报告也不是闭环完成。

**时点与责任**：在对应平台适配和真实闭环验证前落实；不要求现在选定全部商业指标或恢复 AI 策略算法扩展。

### A-07 / P2：验收场景充分，但尚缺本轮可执行的验收基线

**证据**：[验收文档](acceptance-plan.md#验证前需要落实)、[验证准备末段](verification-readiness.md#后续真实发布与反馈)明确样本、并发、延迟、恢复时间及完成率待实测前确定。V-01～08 是步骤安排，不是已执行测试结果；现有九组原型检查不覆盖真实服务、设备和发布。

**最小闭合产物**：为每个即将交付的核心场景设置稳定用例编号，关联需求、前置配置、实际资源、操作步骤、预期结果、证据位置及通过／失败／阻断／未验证。先落实接入、停止及恢复的重复次数、允许延迟和故障观察范围，再随交付扩展。

20–50 台是管理范围，尚不是完整负载模型；需明确实际测试台数、活跃任务／并发、持续时间、网络分布、队列积压及恢复判据。探索可以先测量，不得事后把测得结果定义成通过线。

**时点与责任**：测试与技术工作在对应验收开始前固定判据。Web 继续用 Playwright 从实际入口操作；Android 原生授权和真机能力另外留真实证据，不用模拟或直接改库补通过。

### A-08 / P2：交接文档存在版本与推进出口不一致

**可定位的事实**：

- 根 [README](../README.md)仍称需求对齐到 R-133，当前索引和基线已至 R-141。

- Web [页面规格末段](workbench-page-spec.md#111-原型检查范围)和[原型说明](design/workbench/prototype/README.md#覆盖与限制)仍要求补设计分支后再正式实现；[新推进安排](next-stage-plan.md)则已进入核心交付划分。两者未明确哪些是第一批必要交付、哪些可随实现补齐。

**最小修订**：同步当前版本入口，保留历史事实日期；把未覆盖交互标为对应模块的实施／验证工作，明确正式实现的准入条件，不再用“先完善设计”笼统延后所有开发。补一份精简的三端交接映射即可，无需继续生成图稿。

**时点与责任**：开发交接时修正文档；这是确定性的同步工作，不需重新请用户选择页面或视觉方向。本报告记录问题，未替换已有工作区文件。
