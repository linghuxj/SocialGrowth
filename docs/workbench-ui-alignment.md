DESIGN.md 用设计叙述表达意图，用结构化 tokens 记录具体视觉值。它适合沉淀视觉与组件规则；本工作台仍需独立描述任务流程、信息组织与业务状态。根目录 [DESIGN.md](../DESIGN.md) 已建立意图与交互骨架，按规范顺序组织当前适用章节；颜色、字体、间距等尚未定稿，待视觉方向及代表页面对齐后补充。

本轮先确定使用流程和内容层级，再通过代表性页面对齐视觉方向，最后落定颜色、字体、间距、组件与状态。未选择视觉方向前不预设品牌色或沿用 Demo tokens。上述运用方法是本项目建议，不是引用规范为本项目指定的界面。

## 2. 使用者与工作目标

| 视角 | 需要完成的工作 | 界面应帮助回答的问题 |
| --- | --- | --- |
| 内部运营 | 准备项目与成品、批准方向、处理异常、评估进展 | 现在需要我做什么？影响谁？处理后是否继续运行？ |
| 产品与业务负责人 | 判断目标和实际执行是否一致，理解改进依据 | 目标是否推进？哪些结论有证据？哪项调整已经落实？ |
| 日常操作者 | 在多个项目、素材和异常之间连续工作 | 我在哪个项目？刚才的输入还在吗？返回后能继续原来的处理吗？ |

产品与业务负责人是观察视角，不新增权限角色。首期内部运营同权，负责人仅承载责任和提醒；客户不登录工作台。设备提供者使用独立 App，工作台承载运营侧的设备、提供者与基础分佣处理。

已确认职责意味着：常规任务无需逐条批准；待办集中呈现需要人工决策或处理的事项。AI 正常工作仍可查看依据、进展与结果，不能把“没有人工待办”表现为“系统没有工作”。

## 3. 日常入口：跨项目待办优先（UI-001 已确认）

场景：运营早上进入工作台，多个项目正在运行，其中一个需要账号验证，一个待补素材，其余正常执行。

| 方案 | 工作顺序 | 取舍 |
| --- | --- | --- |
| A，已选择 | 跨项目待办与异常 → 具体项目或处理现场 | 减少跨项目遗漏；需要在待办内保留充分的项目上下文 |
| B | 选择项目 → 项目准备、执行、效果 | 项目上下文连贯；跨项目问题需要另设明确提醒 |
| C | 各项目目标与效果总览 → 偏差 → 处理 | 便于业务巡检；数据延迟时容易低估执行问题 |

2026-09-27 用户对 Q1 回答“A”，确认先处理跨项目待办和异常，再进入具体项目。后续 Q2 选择全部项目默认可见，详见 UI-002；这些选择不改变 AI 自主范围、运营同权或项目资源专用规则。

### 根据 UI-001 展开的首页建议

首页负责“找到需要我行动的事项并进入处理”，项目页负责“理解该项目的完整准备、运行与效果”。待办详情保留项目、账号和设备上下文，提供相关记录与项目入口，避免为查一项异常反复切换页面。

| 首页内容层级 | 呈现内容 | 操作目的 |
| --- | --- | --- |
| 主要区域：需要行动 | 阻断、必要人工验证、待确认的方向变化及需要补齐的资料；标明事项类型 | 明确需要运营做什么，不把正常 AI 执行列成人工审批 |
| 跟进区域：处理后的进展 | 已提交处理但尚待复核、等待执行端停止确认等事项 | 能追踪结果，不因点击已处理就从视野中消失 |
| 次要区域：运行摘要 | 正常项目进展、近期发布核验与周期要求摘要、数据更新时间 | 处理异常的同时了解其余业务；没有待办时仍能确认运行情况 |

待办摘要建议包含：事项说明、所属项目、影响对象及范围、负责人、等待时长/相关有效窗口、当前阻断和下一步。涉及风险时给出具体依据，不凭错误文字自动标成全局紧急；最终排序规则待后续明确。

同一项目同次故障沿用既定合并规则，一条待办可展开多个受影响任务，各任务分别显示核验及恢复结果。跨项目仅提供汇总查看，不把相似错误合并成一项共同处置。

### 默认显示全部项目待办（UI-002 已确认）

2026-09-27 用户对 Q2 回答“A”，确认首页默认显示全部项目的待办，并可筛选“我负责的”。该选择服务于首期共同运营、跨项目发现问题和代办，不改变项目负责人的提醒责任。

“我负责的”表示本人作为项目负责人的项目范围，不表示仅本人可以处理，也不等同于“我正在处理的事项”。其他运营仍可代办，实际处理人按既有规则记录。无需为这项筛选新增待办认领或转派制度。

由此建议：当前筛选范围与待办数量同时显示；从待办详情返回时保留范围和位置。筛选后没有待办时，文案说明是“当前筛选下无待办”，提供返回全部项目的入口，避免被理解为全局无事可做。这些为交互细化建议，不额外改变权限。

### 跨项目按紧迫性排列（UI-003 已确认）

具体场景：项目甲有一项素材资料待补，项目乙的发布窗口即将结束且仍被阻断，项目丙需要确认下一周期的方向。全部事项都可见，但默认顺序会影响运营的处理习惯。

| 方案 | 默认组织 | 取舍 |
| --- | --- | --- |
| A，已选择 | 跨项目按处理紧迫性组织，事项上显示项目；支持按项目筛选 | 优先看到需要及时介入的事项；处理时可能在项目之间切换 |
| B | 按项目分组，每组内呈现待办及紧迫性 | 便于连续处理一个项目；需要额外留意其他组的紧急事项 |

2026-09-27 用户对 Q3 回答“A”，确认全部项目待办默认按紧迫性排列，优先关注即将错过有效窗口、正在阻断业务的事项，并说明排序依据；保留项目筛选。具体等级、阈值和多因素排序规则尚未确定，不凭本次选择引入任意数值。

排序依据应对应可核对的事实，例如有效窗口、当前阻断和实际影响范围，不让 AI 无解释地给出优先级。沿用同项目同次故障合并、逐任务核验的既有规则；排序不扩大自动执行授权，也不意味着所有结果待核实事项均须人工处理。

### 首页组织的小结与细化建议

已确认的主线为：全部项目 → 按紧迫性查看需人工处理的待办 → 进入事项及相关项目 → 跟踪实际处理结果；可筛选“我负责的”或具体项目。

基于这条主线，建议待办摘要按“要做什么 → 为什么现在处理 → 影响什么 → 当前进展”组织。等待系统复核且暂不需人工行动的事项放入跟进视图，避免与需要行动的事项反复争夺首位；复核发现仍需人工处理时再明确提示下一步。

列表更新时保留用户正在阅读或处理的事项位置，提示新出现的紧急事项及刷新入口，避免自动排序造成误点。有效窗口已过时改为说明超窗及所需处置，不能继续显示为尚可按原授权执行。这些是交互建议，尚未固定刷新、布局或视觉样式。

## 4. 信息组织与导航

以下为业务内容分组，不等于七个一级菜单。默认入口已按 UI-001 采用跨项目待办优先，导航主结构按 UI-009 采用全局入口与项目内业务页面；具体页面组织建议见下文。

| 内容区域 | 核心内容 | 用户的主要动作 | 内容归属建议 |
| --- | --- | --- | --- |
| 工作概览与待办 | 需决策/需处理事项、影响范围、负责人、近期执行及周期进展 | 定位问题、进入处理、检查处理结果 | 全局汇总；详情保留项目上下文 |
| 项目 | 目标与批准范围、准备进度、账号阶段、当前周期、后续安排、效果摘要 | 建立项目、补齐资料、确认方向、暂停/恢复/结束 | 项目作为主要业务上下文 |
| 成品素材 | 文件预览、来源、业务事实、语言与版本、商品/剧集关联、准入结果 | 批量上传、人工关联、补充、更正、撤回 | 以项目内操作为主；全局检索是否需要待确认 |
| 发布安排与结果 | 计划时间、平台形式、发布身份、内容版本、执行进展、核验证据、阻断 | 查看安排及依据、处理异常、核对实际发布 | 项目视图与跨项目筛选使用同一事实 |
| 效果与复盘 | 主目标、引流完成数、可得效果、窗口/截止时间、复盘依据、后续落实 | 理解偏差、确认方向变化、追踪改进结果 | 项目周期为主，账号与内容逐层下钻 |
| 账号与设备 | Page/频道、当前项目、执行手机、提供者、准入/授权/运行条件、交接 | 首次分配、登录协助、接管、换机与跨项目交接 | 全局资源入口；项目内显示已分配资源 |
| 提供者与基础分佣 | 邀请接入、本人设备关联、收益依据、承接期间、比例、处理记录 | 邀请管理、核对归属、记录基础处理 | 辅助业务入口，不扩展为完整支付中心 |

项目设置就近承载时区、复盘、观察窗口、目标及通知配置。全局通用设置仅容纳实际需要的全局项，不先搭建通用配置平台。

### 页面目录与跳转建议

| 一级入口 | 页面与主要内容 | 关联跳转 |
| --- | --- | --- |
| 工作台 | 全部项目待办、处理后的跟进、正常运行摘要；按紧迫性呈现需行动事项 | 待办详情 → 对应项目、任务、素材或手机处理界面 |
| 项目 | 项目列表、新建项目、项目概览及准备清单；项目内素材、发布安排、效果与复盘、设置 | 素材 → 对应发布任务 → 核验及效果；复盘 → 后续安排；项目已分配资源 → 全局资源详情 |
| 账号与设备 | Page/频道及手机列表、详情、首次分配、初始化、换机与交接 | 资源 → 当前项目、受影响任务、相关待办与必要接管 |
| 提供者与分佣 | 提供者及邀请接入情况、关联设备、基础收益归属及分佣处理记录 | 提供者 → 本人关联设备、账号承接期间及收入依据 |

项目内页持续显示项目名称与当前位置；进入全局资源详情时仍显示其当前归属，并可返回来源项目或待办。一个资源或任务在多个入口被引用时，详情与处理记录指向同一业务事实，不维护互相独立的副本。

从全局待办深链进入项目任务，应直接定位到相关内容，无需先经过项目概览。跨项目切换前提示尚未保存的输入，切换后更新上下文与数据，不能只改项目标题而保留上一项目的操作对象。

首期页面职责到此已有主结构；具体侧栏宽度、标签形式、详情是否使用抽屉等可逆细节交由代表页面设计处理，不逐项询问。

## 5. 需要逐步对齐的交互主线

### 5.1 从项目准备到 AI 运营：准备清单（UI-005 已确认）

2026-09-27 用户对 Q5 回答“A”，确认先建立项目，再通过可保存、可返回的准备清单，按资料和资源到位顺序补齐。每项说明缺少什么、影响什么，并能直接进入对应处理处。

保存资料、确认初始方向与批准范围、具备执行条件分别表达。首次进入自主运营沿用 R-017：确认初始方向后，在就绪条件满足时按既定范围安排，不新增独立启动审批或逐条发布批准。方向确认的摘要与反馈细化见[页面规格](workbench-page-spec.md#3-项目筹备与设置)。

本次选择考虑了目标已经清楚、成品与账号设备未必同时到齐的筹备场景：

| 方案 | 操作方式 | 取舍 |
| --- | --- | --- |
| A，已选择 | 先建立项目，再通过可保存、可返回的准备清单，按资料和资源到位顺序补齐 | 适合分批筹备；需明确缺项及其影响，避免遗漏 |
| B | 按固定向导依次准备目标、内容、账号设备及运行规则，可保存后继续 | 新手路径更明确；某一步资料未到齐时，后续准备容易被卡住 |

这项选择只确定筹备交互，不改变正式执行的就绪条件与批准范围。保存项目或完成某份表单不自动授予发布许可；尚未填写的实际业务参数继续显示未配置。

#### 准备清单的内容建议

| 准备项 | 运营需要补齐或确认的内容 | 应显示的就绪依据 |
| --- | --- | --- |
| 目标与范围 | 项目业务、受众、阶段目标、初始方向及 AI 可自主调整范围 | 哪些资料已保存、哪些方向或范围仍待确认 |
| 成品与业务资料 | 成品来源、业务事实、商品或短剧、语言/版本/集序关联 | 文件结果、人工资料完整性、准入检查分别呈现 |
| 账号与手机 | 公司发布身份、项目分配、执行手机及必要初始化 | 已分配、初始化中、身份已核验、仍受阻等事实，在线不代替就绪 |
| 引流与周期规则 | 现成入口、业务时区、周期起点及间隔、引流最低要求、观察窗口等适用配置 | 实际采用值、未配置项及引流路径核验情况 |
| 负责人及提醒 | 项目负责人、收件邮箱及必要提醒配置 | 已配置与发送/送达事实分开，不用邮箱已填写冒充通知可达 |

上述分组是页面内容建议，不强制填表顺序。每项提供直接补齐入口及返回项目清单的路径；允许独立准备的事项不因其他分组缺项而不可编辑，真实业务依赖仍须检查。

筹备页建议使用“还缺什么、阻断什么、下一步是什么”汇总，避免只显示一个百分比。初始就绪后，项目页转向日常安排、待办与效果，原配置和准备证据仍可查看；具体切换呈现待页面设计确定。

### 通用交互建议

- 工作参照：运营人员持续处理项目和问题的桌面工作台。首屏帮助发现并完成工作，长表用于比较，详情用于理解和决策。信息密度、默认列与屏幕适配需通过实际工作场景确认。
- 返回连续性：从列表进入详情后，返回保留筛选、页码和浏览位置；从全局进入项目时清楚显示当前范围。刷新不得静默丢失已输入资料或将旧事实写回。
- 表单：字段说明贴近输入，错误定位到字段，区分必填、可稍后补充和缺失导致的具体阻断；未知业务数值保持未配置，不以示例自动生效。
- 长耗时动作：显示请求已受理、进行中、成功/失败或待核实；允许离开再返回查看。重复点击不重复产生业务动作。
- 有业务影响的操作：对暂停、结束、撤回、更正、撤下及交接分别说明对象和影响；确认信息使用当时的任务事实，变化后重新检查。常规查看和保存不堆叠确认弹窗。
- 状态表达：文字与图形共同表达，颜色作为辅助；明确数据更新时间，失联时显示最后已知状态。正常运行也保留可见进展，避免首页只剩红色告警。
- 数据阅读：列表摘要只放能帮助判断和行动的信息；来源、统计区间、时区、缺失与归因粒度可追溯。不同口径不拼成虚假统一趋势。
- 操作可达：可见焦点、键盘完成主要表单与对话框、错误和禁用原因可读；不把解释只放在悬停提示内。

## 9. 后续验收场景草案

这些是设计覆盖检查与未来 Playwright 真实 Web 验收的候选，不是已执行测试或通过证据。

1. 运营从全局或项目入口定位异常，完成处理后能区分复核中、已恢复及仍受阻，返回列表仍保留筛选。
2. 批量上传部分失败，已成功文件与已填资料保留；人工关联完成后进入候选，不产生未经范围批准的发布。
3. 某任务提交后失联，页面显示待核实及最后更新时间，不把重发作为普通恢复动作。
4. 两名运营打开同一手机处理页，未获控制者不能操作；原处理者交还后必须复核当前手机事实。
5. 素材更正或撤回时清楚展示影响，未提交、编辑中与提交未知的任务分别处理，无关任务继续。
6. 项目暂停后不启动新发布，已发布效果仍按条件采集；提供者暂停手机时该手机不继续采集，未决结果保留。
7. 复盘显示观察窗口未满或数据延迟，未知不变为零；有依据的调整可追溯至实际后续任务。
8. 运行中修改周期配置时显示本周期仍用原值、下周期生效时间；历史证据及统计口径保留。

实现阶段依仓库纪律使用实际 Web 入口与 Playwright，并保留脚本、命令、环境、断言及必要脱敏截图。真机相关验证需要实际设备与 Artemis；本文不启动服务、不执行发布，也不新增业务验收结论。
