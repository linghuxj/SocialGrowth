# 分散手机接入：VPN 与 mDNS 可行性核查

日期：2026-09-25。状态：官方资料与局部代码核查完成，未部署 VPN、未连接实机、未进行容量测试。以下技术方案为建议，尚未被选定。

## 已确认约束

- 首期 20–50 台手机，多地点分散部署；允许分批执行与排队，并发上限可配置，不要求全量同时执行。
- 各地点只能部署手机，不能依赖现场网关或常在线电脑。
- 设备按项目分配，同一平台固定发布身份。
- 手机统一 Android，允许安装手机端代理 App 并完成必要系统授权。
- 已有设备型号和系统版本混合，首期只需兼容选定范围；具体范围与权限机制待明确。
- 使用原厂 Android 系统，不允许 Root 或系统改造；采用安装代理及必要系统授权的方式。
- 重启、权限失效时允许现场人员协助解锁或重新授权，之后由 AI 复核恢复；日常运行不以现场操作为前提。
- 管理连接使用专门通道；部分国内手机的 FB、YT 还需要单独的业务上网通道，用户以“两套 VPN”描述此需求。

## 初步结论

管理 20–50 台分散手机在架构上可行，但不能仅凭 VPN + mDNS 确认可长期无人值守运行。需要分别解决网络连接、设备登记、操作权限、可靠任务执行和掉线恢复。实机与网络条件决定可行性边界。

mDNS 使用本地链路多播进行名称与服务发现；标准不能保证多地点 VPN 设备自动构成同一发现范围。即便添加反射、代理或支持多播的覆盖网络，还需验证手机上的服务是否在相应接口发布、返回地址是否可达，不能只验证服务名可见。[RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html)

Android ADB 的无线调试文档要求配对，并使用 mDNS 发现服务；官方流程基于同一无线网络。该机制不能直接证明无现场主机、跨 VPN 的控制可用。Android 版本与 ADB 版本有差异，应按实际设备核验。[Android ADB](https://developer.android.com/tools/adb)

## 建议验证的接入方案

手机上的执行代理主动通过经过认证的 TLS 连接接入中心，完成设备登记、心跳、任务接收与事件回传；VPN 可为此提供私有管理网络。是否必须经过 VPN，需结合现有网络与访问要求确定。

- 登记使用稳定设备身份，关联项目、平台账号和获准能力；IP 与 mDNS 服务名仅为连接信息。
- 通过心跳判断连接活性，分别记录网络在线、执行能力就绪与账号可用状态。
- 任务、确认与回执采用单播应用协议，例如 HTTPS / WSS；mDNS 服务公告不承担业务通知与可靠交付。
- 断线重连后对账任务状态。结果未知的发布先核验，不因超时或重连直接重复执行。
- AI 可在中心作决策，手机代理执行获准操作；安装代理、连接网络与获得截图/操作能力须分别验证，不能把“代理在线”视为“可以控制任意 App”。

此设计不依赖现场网关。若不能安装代理，则需要另行验证中央控制端经 VPN 直连手机调试服务的方案，重点核验配对、接口监听、实际端口发现、重启恢复及授权持续性；目前不将其视为已可用替代方案。

## Android 条件与运行限制

若采用 Android，需要考虑后台服务与启动限制，测试锁屏、省电、应用被终止和重启后的表现，不能承诺单靠常驻连接即可持续运行。[前台服务后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

同一 Android 用户或工作资料只允许一个活动 VpnService；若手机已有另一业务 VPN，不能默认两个 VPN App 并行。管理连接与普通应用流量的路由需要明确，VPN 连通本身不授予设备操作权限。[Android VPN](https://developer.android.com/develop/connectivity/vpn)

## 两套 VPN 用途的实现核查

用户新增要求：管理连接与部分国内手机的 FB、YT 上网分开。用户已确认需要两条用途独立的逻辑通道，不强制两款 VPN App；需要区分网络用途与系统 VPN 实例。

Android 同一用户或工作资料只有一个活动 VpnService，启动新的服务会停止旧服务。系统支持按应用决定是否进入该 VPN，但按应用分流本身不会创建第二套系统 VPN。[Android VPN：服务限制与按应用分流](https://developer.android.com/develop/connectivity/vpn)

建议优先研究同一客户端、单个 VpnService 内维护管理和业务两套逻辑隧道或出口，按管理目的地址及业务规则分流。此为架构候选，不表示任意现成 VPN 客户端均支持，也不保证两条通道具有独立进程级故障隔离。需要验证 DNS、IPv4/IPv6、中心地址可达性、业务通道故障后的管理连接、手机重启及网络切换。

若必须使用两套现成 VPN App，需先检查是否都占用同一用户的 VpnService；不能仅靠允许或排除应用列表解决两个服务互相停止的问题。工作资料是独立作用域，但会引入应用放置、管理与控制范围问题，当前不默认采用。以业务 VPN 配合独立加密管理连接替代管理 VPN，则改变用户当前设想，需另行对齐。

## Tailscale 候选方案核查

官方资料：

- 默认 Tailscale 组网不改变公网流量出口。Exit Node 可转发非 Tailscale 的公网流量，每台手机须单独选择使用出口节点；Android 客户端支持该能力。[Tailscale：Exit nodes](https://tailscale.com/docs/features/exit-nodes)
- Android 支持按应用分流，被排除的应用及其 DNS 不经 Tailscale；不能把需要访问 tailnet 控制中心的管理代理错误排除。[Tailscale：Android app-based split tunneling](https://tailscale.com/docs/features/client/android-app-split-tunneling)

基于上述能力的候选设计（推论，尚未实测）：

- 手机上的管理代理通过 tailnet 地址连接控制中心。
- 有业务出口需求的国内手机选择部署在能够访问目标平台网络中的 Exit Node，FB、YT 公网流量经该节点转发。
- 无额外业务出口需求的手机不必启用 Exit Node。
- 可以让同一个 Tailscale Android 客户端承载这两种用途，不必因此再运行第二个系统 VPN。逻辑路由分离不代表客户端、协调服务与底层网络故障彼此独立。

仅默认安装 Tailscale 不会自动解决目标平台访问问题；出口节点的存在也不证明国内手机一定能稳定连通。应以实际运营商、Wi-Fi/蜂窝网络、控制服务和出口节点测试为准。需验证 DNS、IPv4/IPv6、登录与素材上传、时延和带宽、锁屏重连，以及出口不可用时管理连接是否仍可用。Exit Node 不解决 mDNS 跨地点发现的前述问题。

## 现有代码的局部事实
