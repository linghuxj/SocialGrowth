## 输入准备与使用时点

以下责任表示工作分工，不新增产品权限角色。业务输入由运营提供，技术事实由设计与验证工作整理；未知值如实保留，示例及 Demo 参数不作为默认答案。

| 准备事项 | 谁提供或核验 | 必须落实的时点 |
| --- | --- | --- |
| 国家语言、阶段目标、批准范围、来源与真实成品、商品/剧集/版本资料、现成引流入口 | 运营及业务提供方 | 形成对应可执行安排前；项目资料可分批准备，不要求无关输入全部完成 |
| 公司媒体账号及具体 Page/频道、平台资格、权限、手机分配 | 运营提供，系统及实际平台核验 | 对应资源进入执行前；正式开通后的目标提前批准，满足 R-131 条件才自动切换 |
| 周期时区与首次起点、最低引流数量、频率/有效窗口、负责人和邮箱 | 运营 | 使用相关配置前；默认 7 天复盘、每日采集尝试、恢复 2 次/5 分钟可明确采用，其他数值不凭空补齐 |
| 指标定义、实际数据源、权限、覆盖区间与观察窗口 | 运营明确业务意义，验证工作确认来源能力 | 对应效果比较前；没有足够数据不强行优化，维持获准有效安排 |
| 原已通过的机型/系统、ADB/Artemis、中心连接方式与任务证据 | 从既有记录及用户验证中整理 | 设计复用范围和增量验证前；记录未整理齐不等于推翻用户已确认的通过事实 |
| 候选手机、现有 Wi-Fi、中心与出口、测试账号及模型条件 | 资源盘点与验证工作 | 对应实测前；历史采购计划不等于当前缺失或已部署，不自行采购 |
| 场景样本、并发、延迟、完成率、重连/恢复与容量判据 | 验证工作据执行窗口及真实资源提出并明确 | 对应验收开始前；不能观察结果后反推通过线，初次探索只形成测量证据 |
| 统一分佣比例与生效点、到账依据及承接期间 | 运营 | 真实计佣前；具体付款安排在实际付款前落实，不阻塞媒体闭环设计 |

## 技术设计要回答的问题

| 设计主题 | 需要形成的可核对结果 |
| --- | --- |
| 业务 AI 与执行衔接 | 获准任务如何携带项目、发布身份、内容版本、有效范围和预期结果；系统校验与 Artemis 执行如何关联，不能以模型自报完成代替业务核验 |
| 任务和事实保存 | 如何保存批准范围、任务及安排版本、素材、分配与承接期间、实际发布及效果证据；备份与恢复须保住未决任务、暂停及撤权事实，不能仅有备份文件却未验证恢复；服务重启、重复回执或 AI 会话更换后不丢失暂停和未决事实 |
| 客户端与网络接入 | 邀请、注册、一人多设备、系统授权、官方 Tailscale 配套、中心首次 ADB 配对、端点更新与退出回收如何衔接；入网不等于获得运营权限 |
| 文件与平台适配 | 素材如何到达指定手机并被准确选取；FB 视频/图文、YT Shorts/常规视频如何执行和核验，数据从何种获准渠道回收 |
| 操作与恢复 | 跨平台/任务类型的单机界面互斥、队列、项目暂停与提供者暂停的区别、停止确认、接管交还、掉线/重启、换机与跨项目交接如何保持真实状态和不重复执行 |
| 部署与支持范围 | 中心/出口及模型选择、配置与凭据处理、客户端安装更新、支持机型版本和运行容量；明确凭据录入/更新/失效、敏感界面截图或文字在送入模型前的保护方式及证据保存范围；选型附理由及验证依赖，不因 Demo 已有组件就直接沿用 |

业务对象与关系已经具备建模依据，具体模块、接口、数据表和组件由技术设计形成；不为每条验收场景单独建系统，也不先建通用规则引擎或策略平台。

## 验证推进顺序

| 顺序 | 要证明的结果 | 主要依据 |
| --- | --- | --- |
| 1. 复用与盘点 | 既有通过、受变更影响及尚未覆盖的范围清楚，测试资源和授权可核对 | 用户原验证、实际环境及本文件输入清单 |
| 2. 接入与网络 | 受邀手机在现有 Wi-Fi 下完成必要授权、运营分配和初始化；管理与业务上网同时可用，端点变化和退出不绕过边界 | [配套验证](research/vpn-mdns-device-connectivity.md#配套客户端的验证安排)、[ADB 核查](research/vpn-mdns-device-connectivity.md#adb-端点发现首次授权与恢复核查2026-09-27)、[入网与权限](research/vpn-mdns-device-connectivity.md#tailscale-入网身份访问范围与退出核查2026-09-27) |
| 3. 真实媒体流程 | 人工素材 → AI 有效安排 → 手机准确选取 → Artemis 执行 → 平台实际内容对应；未知结果不重发 | [业务流程](business-workflow.md)、[平台研究](research/platform-and-android-feasibility.md) |
| 4. 真实反馈接续 | 来源、范围和粒度可核对，反馈进入维持/调整依据并落实到后续任务及执行 | [数据窗口研究](research/effect-data-time-granularity.md)、[验收](acceptance-plan.md) |
| 5. 异常及完整覆盖 | 完成首期平台/内容形式、人员与资源变化、20–50 台管理及基础分佣记录的验证 | [首期完成判定](acceptance-plan.md#首期完成判定) |

这些步骤允许迭代。少量资源先探索不缩减首期范围；出现与已确认边界冲突的实测结果时集中回到对应决策，不自动换引擎、增加现场网关、放宽 Root 限制或制造成功证据。

## 证据与实施边界

验证记录至少包含需求依据、环境及版本、输入与生效配置、实际操作、结果、证据位置和局限，状态分别为通过、失败、阻断、未验证。基础链路已通过与新客户端/规模尚待验证可以同时成立；不将平台商业成绩作为系统技术通过的替代品。

当前已完成需求对齐及技术设计初稿、证据盘点和验证步骤；未在本轮启动服务、实施客户端、执行发布或付款。后续操作既有 Demo、原型或新方案均遵循[工程规范](../CLAUDE.md)；技术事实由资料和实测核查，只有影响业务结果的真实新歧义才继续请求确认。
