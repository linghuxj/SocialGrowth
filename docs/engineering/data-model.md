# 首条闭环：持久化模型与状态约束

版本：design-v1，2026-09-19。状态：开发规格，未部署、未迁移、未完成应用实现。依据为 [G-01 至 G-05](../handoff/2026-09-19-business-flow-proposal.md)；本文件把既定业务事实映射到存储关系，不新增业务取舍。用于修复 B-01/B-02；当前演示 SQL/JSON 不代表本规格已经落库。

## 实体及必需关系

名称为本版工程设计命名。ID 为不透明字符串；时间保存带时区时间点，排期另外保留业务时区。关联对象不得只保存显示名称。草稿可不完整，批准和执行时必须满足对应条件。

| 实体 | 主要字段 | 关系与约束 |
| --- | --- | --- |
| `parties` | `party_id`、名称 | 标识客户、所有方及授权方；同一主体可有多个角色 |
| `projects` | `project_id`、`client_id`、`goal_version_id`、受众、服务期限、责任、状态 | 每个项目指向客户；目标变更产生版本，历史发布引用原版本；退出不删除历史 |
| `accounts` | `account_id`、平台、名称、`owner_party_id`、生命周期状态 | 所有方与服务客户分开；凭证只存安全引用，不能将持有密码等同授权 |
| `account_service_relations` | `relation_id`、`account_id`、`project_id`、`client_id`、`authorizer_party_id`、`authorization_ref`、`allowed_actions`、`allowed_data`、有效期、撤回时间、共享批准引用 | 保存历史关系；默认同一时期客户专属；重叠服务须有有效共享批准及范围/期间、目标冲突和归因说明，不能用 accounts 上单一 client_id 覆盖共享例外 |
| `device_bindings` | `binding_id`、`device_id`、平台、`account_id`、生效/结束时间 | 同设备同平台的有效区间不重叠，账号路由同时核对平台与绑定；设备在线不表示业务获准 |
| `content_identities` | `content_identity_id`、来源/剧情依据、`allocation_status`、`assigned_account_id`、归属版本、`first_published_at` | 所有语言/字幕/封面变体共同引用；`allocation_status = unallocated / reserved / assigned_locked`，不包含 published；首次已发事实不可因删帖、退出或改名清空 |
| `slice_metadata` | `slice_id`、`content_identity_id`、语言、字幕/配音说明、文件引用、SHA256、时长、比例、权利记录引用 | 多文件对一身份；文件哈希用于校验，不充当跨语言内容身份；身份级排他，不在每个语言文件复制独立锁 |
| `content_reviews` | 身份/版本、权利范围与期限、适配结果、重叠对象、人工结论和依据 | 主体不同的少量剧情衔接经人工确认可分属不同身份；未确认不作为合格库存；不设自动放行秒数或比例 |
| `strategy_versions` | `strategy_version_id`、项目/目标/规则版本、账号、身份/文件、文案、入口版本、排期/时区、观察计划、状态 | `draft / approved / rejected / invalidated`；保存和生成都不是批准；改动产生可追溯版本，不能沿用受影响的旧批准 |
| `approvals` | `approval_id`、指定策略版本、批准人/时间、范围、有效期、发布量/成本、停止条件、撤销记录 | 新试验先批准；执行时再次核对版本和实际权限，数量与成本取项目批准值，不设全局默认承诺 |
| `task_directives` | `task_id`、`attempt_id`、项目/批准/策略版本、账号/设备绑定、身份/文件、计划有效期、`execution_status`、暂停引用 | 技术状态 `pending / dispatched / executing / waiting_human / completed / failed / cancelled`；取消只适用于确定尚未提交且已停止的安排；不以 failed 推导发布失败 |
| `publication_attempts` | `attempt_id`、任务、身份/文件、账号、`publish_status`、提交证据/时间、公开标识/时间、证据引用、核对人/时间 | `not_submitted / in_progress / unknown / confirmed_not_published / published`；明确未发布须有依据并排除处理中/已公开；撤下另记事件，不能改回未发布 |
| `execution_events` | `event_id`、任务/尝试、来源、发生/接收时间、技术状态、发布事实、证据引用 | 追加留存；重复事件不重复计数；迟到的公开证据可补记事实，不能重新激活旧批准或覆盖已发历史 |
| `incident_scopes` | 异常原因、关联账号/设备/内容权利/目的地/服务范围、确认依据、暂停/恢复记录、责任 | 范围无法排除关联先暂停；确认无关联且批准有效才继续；人工恢复与设备资源恢复分开 |

入口、短链和指标记录继续按现有业务范围维护，同时关联项目、账号、内容（仅在实际可归因时）、目标版本和来源。频道级入口不能强行填单条 `slice_id`。上述表不是原演示 SQL 的可直接执行迁移。

## 内容状态转移及原子边界

所有判断读取**身份下全部版本及尝试**，不能只看当前文件。数据库事务必须锁定同一 `content_identity_id` 的权威归属行，或使用等效的原子并发保护；Redis 锁仅作辅助。批准、创建可执行安排、状态变化须检查同一归属版本，不能只建立 `(slice_id, allocation_status)` 唯一索引。

| 动作 | 必须满足 | 写入及拒绝行为 |
| --- | --- | --- |
| 预占/独占分配 | 身份与权利已核对，无已发历史，无冲突归属或未解决尝试，目标账号合格 | 同事务确定账号与版本；竞争方得到归属冲突，不能给两个草案同时执行资格 |
| 执行提交 | 指定批准仍有效，当前身份归属为目标账号；无已发、进行中或未知尝试；资源与排期合格 | 提交前登记尝试及执行状态；可能已提交但无可靠结果时记 unknown，不自动重试 |
| 未提交取消并释放 | 所有版本均确定未提交、无发布历史；全部旧批准与执行安排已失效且无在途提交可能 | 同事务撤销并释放；未知、进行中、曾提交后明确失败均不满足自动跨账号释放条件 |
| 确认从未发布后原账号恢复 | 明确未发布证据、排除仍在处理；人工复核异常、原账号权限、批准及新排期 | 新尝试关联原失败记录；不覆盖旧尝试，不转移账号，也不允许已有发布历史再次提交 |
| 收到公开证据 | 证据与尝试/账号/内容相符 | 记 published 并保留首次已发事实；迟到/重复证据不增加合格发布次数 |
| 下架、客户退出或删文件 | 有相应权限或实际事实 | 追加后续事件；归属和已发历史保留，不恢复发布资格 |

`reserved` 不配置未经业务确认的自动释放时限；即使技术租约到期，业务释放也必须满足上表。技术重传同一个消息不等于允许新建一次发布尝试。

## 旧数据接入与迁移核查

1. 保留旧记录和来源；按内容核查建立共同身份，不默认“一文件一身份”或“同哈希才是同内容”。无法确认的标记待核查，不进入可执行库存。
2. `published` 旧值迁移到发布事实前核对来源及账号；原 `failed`、`completed`、超时、`unallocated` 不能单独证明实际发布与提交历史。证据不足保持待核查，不批量释放。
3. 账号所有方、授权、客户及共享例外从实际记录补齐；未取得不得制造默认授权、有效期或归属。
4. 分别验证历史引用保留、并发分配、跨语言同账号/跨账号重复、未知结果、取消释放、失败恢复和退出。测试场景见[离线验证规格](offline-verification.md)。生产迁移需在相应部署任务核对真实存储与数据，本轮没有执行。
