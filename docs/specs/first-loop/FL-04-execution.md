# FL-04：执行与异常核对

状态：规格已整理，应用实现及验收未完成。属于用户确认的首批开发范围；发布 Issue 不触发代码实现或真实运营动作。

## 问题陈述

当前调度按平台寻找设备并直接构造成功 URL，设备配置还保留模拟器示例；这既不能保证不串号，也无法处理丢回执、未知发布、身份挑战和人工恢复。

## 解决方案与完成标准

- [ ] 落实设备/平台/账号当前绑定的精确路由，无空闲专属设备则等待，不借调；移除模拟器实际配置与执行支持，保留离线数据替身。
- [ ] 中枢与 Agent 按统一 design-v1 实现 Pull、指令、回执、身份/批准校验及错误语义，替换占位成功路径。
- [ ] 设备资源、技术状态和发布事实分开；失败/超时不推定未发布，未知不再次提交或释放。
- [ ] 同消息/尝试去重；迟到公开证据补记历史但不恢复旧计划；冲突证据保持核查。
- [ ] 按共同原因暂停受影响及不能排除关联范围，确认无关联且批准有效者可继续；人工恢复需核对证据、权限与排期。
- [ ] 挑战、设备复位或验证码成功均不自动恢复业务；明确从未发布后经批准可原账号新尝试，过期安排不补发。

## 用户故事

1. 作为运营人员，我希望任务只发送给目标账号当前绑定设备，以便不串号执行。
2. 作为异常处理人员，我希望区分未知、已公开和明确未发布，以便不会在断线后重复提交。
3. 作为有权限的恢复人员，我希望核对影响范围和当前批准后恢复，以便验证挑战或资源恢复不掩盖业务限制。

## 实施决定

沿用纯物理真机原生 App UI 执行，不改成官方发布 API。中枢/端侧采用一套传输适配及统一载荷，选 WS 或 gRPC 后记录理由并同步两端；不并建两套。使用现有 design-v1 状态/错误/事件语义，持久化去重和业务事实，不能仅依赖进程内锁。旧 TASK-01～04 纳入本任务。

## 测试决定

覆盖 T-01 及 T-05～12、C-04/05/09/12/13/14；可控时间、丢失/乱序/重复回执及相关/无关任务样例。断言实际提交次数、身份归属、暂停范围、批准与历史。另验证真机绑定、原生 App 动作和可核对发布证据，只有在有效实际授权下执行；缺接入时明确标注待真机验证。

以上为待执行的应用验证计划；此前通过的文档/样例结构检查不能替代。本任务完成记录应附实现提交、实际测试命令与结果、受控及真实接入范围。

## 不在本次范围

不自动发布真实客户内容、购买设备/代理、改用模拟器或自动规避平台限制；不承诺 24 小时人工响应。
