## B-01：旧数据模型确有缺口，不能把指定表名当作业务要求

**证据**：[交付规格 7.1](../delivery-specification.md#71-数据存储与实体持久化模型设计)当前第 390–396 行：`slice_metadata.allocation_status` 包含 `published`，没有内容身份与多语言文件版本的显式关联；`accounts` 未描述所有方、服务关系与授权；`task_directives` 只列执行类状态，没有独立发布事实和待核对结果的映射。该节以“Schema 约束”呈现，仍有被直接当作完整实现基准的风险。

逐点判断：

1. **分配与发布混用属实**。现有示例不能完整表达 G-03a 的“所有版本均未提交且无历史才可释放”，也不能将执行失败与明确未发布区分。问题在业务事实表达不足，并非某枚举中出现单词 `published` 就必然使所有实现错误。
2. **共同内容身份缺失属实**。文件级 `slice_id`、`sha256` 与 `(slice_id, allocation_status)` 不能单独约束同内容的不同语言/编码文件；`slice_id` 已是主键，该联合唯一约束也没有新增跨内容版本约束能力。但 G-03 要求的是统一身份、归属及发布资格，不强制物理表必须命名 `content_identities`。
3. **账号关系表达不完整属实**。只给 `accounts` 增加一个当前 `client_id` 并不能完整涵盖 G-02a 已批准共享的范围/期间和历史关系。原报告的四字段方案可供设计参考，不能原样作为已批准且充分的修复。
4. **任务与发布事实映射缺失属实**。保留 `pending/completed/failed` 等技术状态本身不违反 G-04a；必须另能记录人工等待、发布事实、暂停及恢复依据，不能把 `failed` 自动解释为未发布。具体采用字段、关系表或事件记录仍由工程设计决定。

**源码抽查补证**：[SQL 说明](../../apps/web-console/data/schema.sql)第 24–58 行及当时的 `lib/db/types.ts` 中 `AccountEntity`、`ClipAssetEntity` 保留旧表达；历史 Web 类型已于 2026-09-20 移除，可从 Git 历史复核。[AI 类型](../../services/ai-engine/src/types.ts)的 `SliceMetadata` 没有统一内容身份或独占字段。不是仅靠新增表名就能证明各层已经一致。

**边界**：当时的 `lib/db/client.ts` 直接导入本地 JSON；该演示读取层已于 2026-09-20 移除，可从 Git 历史复核。不能把 SQL 文件视为已部署 PostgreSQL 的实测结构。本次确认的是仓库模型缺口，不推定线上已有错发。后续应对照 G-02/G-03/G-04a 核对受影响模型和迁移/验证方式；本次未修改 Schema 或业务代码。

## B-02：TASK-05 属实，不能连带认定 TASK-02/04 的旧业务解释仍有效

**证据**：[原研发交接任务书](2026-09-18-developer-handoff.md)：

- 第 16 行已声明示例和实现状态未复验、不同处后续同步；TASK-05 的 G-03 补充再次声明旧字段示例不是完整业务定义。因此“审计此前完全没有识别这些旧例子”的解释不成立。
- TASK-05 仍展示三态 `SliceAllocationStatus`；匹配条件只拦其他账号，无法单独阻止原账号重发已发内容，也没有跨语言身份及未知结果规则。**旧例子不足且有误用风险属实**，后续实现不能仅增加这几个字段就验收 TASK-05。
- TASK-02 已写明超时不证明未发布、不释放未知结果，且补充了关联暂停与恢复验收。TASK-04 已写明验证码完成不等于业务恢复。原报告没有给出这两项现行正文再次要求“超时直接恢复/验证后直接恢复”的证据；将两者与 TASK-05 并列为同一种残留错误，**证据不足**。

**处置**：保留既有 TASK 编号和当前业务补充。TASK-05 后续工程示例需对齐；TASK-02/04 的具体类型、实现及验证依旧待工程落实。原任务标题或早期技术参数不能覆盖当前修订，也不需要重新要求用户选择已确认的 G-04a。

**直接反证**：[Controller README“接口协议与动作流规范”](../../apps/artemis-controller/README.md#三-接口协议与动作流规范-action-protocol)第 34–96 行已有 `PublishTaskDirective` 字段表、`ActionStep` 类型、`ExecutionReceipt` 字段以及错误码示例。即使遵守原报告“只看文档”的范围，也不能说报文完全未规范化。

**成立的缺口**：[Controller 源码类型](../../apps/artemis-controller/src/types.ts)第 33–59 行确有上述指令/回执接口，但和 README 不一致：

| --- | --- | --- | --- |
| 素材 | `mediaDownloadUrl`、`mediaSha256` | `mediaAssetPath` | 输入字段不一致 |

另按 `docs/`、`apps/`、`services/` 当前文件与类型检索，未找到覆盖所有服务边界并与 G-03/G-04a 对齐的完整线协议规范或 OpenAPI/Protobuf 定义；部分 TS 类型也不等于已建立网络协议。[调度源码](../../apps/artemis-controller/src/scheduler.ts)第 41–51 行仍为本地占位回执，不能视为真实 Agent 联调证据。

**处置**：在相应服务联调前统一具体输入输出、异常与业务状态语义，复用现有契约材料。OpenAPI、Protobuf 或其他表达方式是工程选项，缺少指定格式本身不是业务缺陷；不能由此宣称所有独立模块均不能并行开发。

## B-04：没有完整测试替身规范，不等于禁止或无法离线测试

**属实部分**：本次仓库检索未发现专门的 Agent 测试替身规格、配套设备契约测试及场景数据集。现有占位执行也不等于可注入断线、迟到回执、未知结果等场景的合格测试替身。

**不成立的推论**：[产品路线](../product-roadmap.md)第 44 行已允许受控样例、替身或接口契约验证。纯真机约束针对实际发布执行，不是要求每个单元测试访问海外手机；本地构造对象/回执也不等于用 Android 模拟器开展真实运营。`DevicePool` 是可在内存构造的对象，不能以缺完整 Fake Device 规范断言任何自动化流水线都无法开始。

**处置**：先按所实现功能定义契约与测试输入，再补足正常/异常分支。设备替身验证、真实设备联调和业务验收分开记录。是否需要独立 Mock Agent 项目取决于具体实现，原报告不能直接将其升级为必建平台或全局开工前置条件。
