## 三、 防重复处理机制与状态流转规则 (Anti-Duplication SOP)

为杜绝后续协作中再次出现“反复审计相同问题”或“代码与文档重复返工”的现象，团队必须执行以下规则：

1. **认领与状态更新**：
   - 开发者开始执行某项任务时，需将本表中对应状态修改为 `🟡 进行中 (In Progress)`，并标注认领人与分支名；
   - 提交 PR 并通过自测后，修改为 `🟣 待验收 (In Review)`；
   - 产品/架构验收通过并合入主干后，修改为 `✅ 已完成 (Completed)`，并填入合入 Commit ID。
2. **唯一可信数据源（Single Source of Truth）**：
   - 本看板为开发整改状态的唯一可信源，后续交接均以本看板为准；
   - “已完成事项”不免于有依据的复审。变更须记录原结论、新证据或用户指令、影响范围、确认结果与替代关系；业务取舍待确认时不得把建议标为已生效；
   - 若出现新增需求或外部变更，必须通过生成新的带时间戳交接任务书（如 `docs/handoff/YYYY-MM-DD-xxx.md`）并在本看板新增记录，严禁私下口头变更。

本次文档复审依照用户 2026-09-19 的明确指令开展，确认与修订进度见[逐项确认与整改记录](2026-09-19-business-flow-proposal.md#8-逐项确认与整改记录)。文档问题复审通过不自动改变代码任务状态或证明真实业务验收通过。

旧TASK是历史整改清单，完整产品范围已在[阶段计划](2026-09-19-product-stage-plan.md)的PG-01至16和[首条闭环规格](../product-first-loop-spec.md)中描述。GRN-09归后续工程拆分，不能因旧TASK未列全前端就认定当前产品规划缺失。本次撤回重复前端映射表，继续复用既有产品成果。

审计原则：先核对最新用户决定、文档效力与适用阶段，再判断缺陷。历史原文不直接视为现行冲突；已知商业待办、真实接入事实及后续工程细化分别管理，不通过审计自动变成新增需求或研发开工条件。

本轮保留开始时已有的审计文件与索引改动，修改状态为本地待审。没有伪填负责人签署、合并Commit或真实平台验收记录。
