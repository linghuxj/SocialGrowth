### RED-02 ⛔ YPP 准入测算存在严重计算错误

> **复核标注 RED-02：已修复**（按最新原则重新梳理）。分母错误成立；审计自身的偏差比例及归档引用不准确。依据、撤回或保留的修改见[逐项记录](2026-09-19-audit-verification.md)。

**涉及文件**：`artifacts/data/3至20台真机设备-前三个月发布与准入测算.md`

文档第四节在反推 YouTube YPP 门槛时，使用"单频累计发布约 135 条"直接相除：

- 300 万 ÷ 135 = 22,222 次/条
- 1000 万 ÷ 135 = 74,074 次/条

然而，文档自己在前文建立的核心假设是 **"50% 观看计入发布当月，50% 计入次月"**。第 3 月末发出的内容有一半播放量要到第 4 个月才兑现，实际在第 3 月末可计入的有效分母应为 **108 条**，而非 135 条。

正确值：

- 300 万 ÷ 108 ≈ **27,778** 次/条（文档写 22,222，**低估 25%**）
- 1000 万 ÷ 108 ≈ **92,593** 次/条（文档写 74,074，**低估 25%**）

**加重情节**：同一项目的历史归档版 `15至50台设备` 测算文档和底层数据文件 `前三个月发布测算-数据.json` 都**正确**应用了跨月折算逻辑（使用累积兑现系数 108 反推，得到 27,778 和 92,593）。最新版 MD 文档反而退化了，与自己的数据源 JSON 产生了直接数值矛盾。

**确认要求**：使用 JSON 中的正确计算结果修正 MD 文档，并重新评估基于该测算做出的所有下游业务决策。

## 七、审计结论

> 以下五点为原审计结论，未获本轮整体认可；按逐项复核，有错误已修正、有历史误读、有外部事实仍待核实。当前分类为6项确定问题已修复、1项历史澄清、20项不成立、2项证据不足；另有4项既有商业待办、2项既有接入核查、4项后续工程细化、1项现阶段不适用、4项可选建议。这些类别不等于新增缺陷或研发阻塞，详见二次复核记录。

1. **首要矛盾**：项目最基础的范围定义——平台数量（2 vs 3）、首月设备/账号规模（4 台 vs 15 台）——在核心文档之间存在根本性冲突（RED-01, RED-03）。这不是措辞问题，而是两套完全不同的启动方案并存，必须由决策者裁定唯一方案。

2. **数据可信度**：当前版本的 YPP 测算文档存在 25% 的数学偏差（RED-02），且与自己的底层数据源 JSON 矛盾。基于该测算做出的任何业务决策都需要重新评估。

3. **预算风险**：技术预算已占公司总盘的 81%–98%，且明确不含设备采购费用（RED-05）。资金缺口是数学上几乎确定的，而非概率性风险。

4. **执行歧义**：开发者交接文档中的 TASK 指令与最新 G 系列业务规则存在直接矛盾（RED-04），工程师无法判断该以哪份为准。

5. **合规缺口**：系统核心方案（UI 自动化）与平台规则（禁止非官方自动化）的冲突被记录但从未被正式处理（ORA-01），缺乏风险评估和应急预案。
