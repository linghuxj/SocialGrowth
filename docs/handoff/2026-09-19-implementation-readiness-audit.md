### 2. 研发与架构视角审查（R&D / Architecture Perspective）

#### 2.1 已具备条件（Positive Findings）
- **长连接 Pull 通信拓扑明确**：确立了 Artemis 纯真机采用 WebSocket/gRPC 客户端主动拉取模型（第 7.2 节），解决了海外真机私网穿透约束；1:1 设备账号强绑定路由（TASK-01）逻辑清晰。

#### 2.2 阻拦进入实施的致命硬伤（Fatal Blockers）
- **【致命阻断 B-01 / P0】底层数据模型（PostgreSQL Schema）严重滞后于最新业务决议，表结构与业务铁律直接对冲**：
  - **复核标注 B-01：旧模型缺口属实，工程对齐未完成。** 当前示例不能完整表达统一内容身份、账号关系及独立发布事实；但指定父表名称、四个账号字段、恰好两个状态字段不是唯一或已批准的完整修法。技术任务状态本身可保留，不能与发布事实混同。影响相关持久化与执行实现，不据此冻结所有独立工作。
  - **修复标注 B-01：工程规格已修复，应用持久化待实现。** 交付规格 7.1 已改用[身份/关系/尝试模型](../engineering/data-model.md)，补并发、历史及迁移核查；旧 SQL 仅保留历史演示用途。
  - [`docs/delivery-specification.md`](../delivery-specification.md) 第 7.1 节的核心 Schema 存在根本性设计缺陷：
    1. **`slice_metadata` 表混淆分配状态与发布事实**：
       - 文档定义：`allocation_status (ENUM: unallocated, assigned_pending, assigned_locked, published)`。
       - **直接冲突**：G-03/G-03a 明确要求“分配与发布分开记录！分配经历未分配、临时预占、独占归属；发布结果另外记录（尚未提交、进行中、公开成功、明确失败、结果未知）”。Schema 将 `published` 强行塞入 `allocation_status`，直接破坏了取消释放（G-03a）和失败恢复逻辑。
    2. **完全缺失 `content_identities`（切片内容身份）实体层**：
       - G-03 核心铁律要求“同一画面片段的多语言字幕/配音版本、封面变化视为同一独占内容，只归属一个账号”。
       - 但 Schema 仅有单层扁平的 `slice_metadata`，没有 `content_identity_id` 与具体视频文件的一对多映射，导致数据库唯一索引根本无法在物理层面阻断跨语言成品的跨账号分发。
    3. **`accounts` 表缺失所有权与客户关系字段**：
       - Schema 中只有 `account_id, platform, bound_device_id, stage`，完全缺少 `owner_party`（所有方）、`client_id`（当前服务客户）、`auth_scope`（授权范围）与 `auth_expires_at`。G-02 客户隔离与授权流转在数据库层完全无法落地。
    4. **`task_directives` 状态机过时**：
       - Schema 定义状态为 `(pending, dispatched, executing, completed, failed, waiting_2fa)`。与 G-04a 要求的“解耦技术超时、人工等待与发布事实（未提交、执行中、结果未知、明确未发布、已公开）”严重脱节。
- **【致命阻断 B-02 / P0】研发交接任务书（`2026-09-18-developer-handoff.md`）代码示例包含老旧错误逻辑，形成误导**：
  - **复核标注 B-02：部分属实，TASK-05 旧示例待对齐。** 任务书已标明旧示例不是当前完整业务定义；TASK-02/04 已补超时、人工等待与业务恢复边界。把三项一并当作仍要求旧业务行为证据不足，不能覆盖已有修订。
  - **修复标注 B-02：旧任务示例已修复，应用 TASK 未关闭。** TASK-05 已移除混合发布态和同账号放行条件，TASK-04 统一指向目标契约；原 TASK-02/04 的有效业务修订继续保留。
  - TASK-05 正文给出的 TypeScript 代码仍定义 `type SliceAllocationStatus = 'unallocated' | 'assigned_locked' | 'published'`，缺失 `contentIdentityId` 与独立的 `publishStatus`。研发人员若按文档代码示例编写，将直接写出违反 G-03 的错误实现。
- **【关键阻断 B-03 / P0】服务间缺少明确的 OpenAPI / Protobuf 接口契约定义**：
  - **复核标注 B-03：部分属实。** Controller README 已有指令、动作及回执字段和错误码示例，源码也有接口类型；“报文未代码化/规范化”的绝对表述不成立。契约与源码不一致、未覆盖当前全部业务分支属实，需在相关联调前对齐；指定 OpenAPI/Protobuf 不是已确认的业务前提。
  - **修复标注 B-03：契约文档已对齐，目标协议待实现。** Controller README 改为源码 v0.1 字段清单；[目标执行契约](../engineering/execution-contract.md)单列 design-v1 载荷、状态及错误语义，不再混用。
  - Web 控制台、调度中枢（Artemis Controller）、AI 引擎与真机 Agent 之间缺乏具象化的接口契约文档，`PublishTaskDirective` 下发报文、`ExecutionReceipt` 上报报文与错误码体系未代码化/规范化，多端协同无法并行。

## 四、 开发实施准入放行条件 (Sprint 0 退出基准)

在正式下发全量编码实施前，必须完成以下修复并通过复核：

1. **[B-01 修复] 升级 Chapter 7.1 数据存储 Schema**：

   - 彻底将 `allocation_status`（未分配/预占/独占）与 `publish_status`（未提交/执行中/未知/失败/已公开）拆分为两个独立状态字段。

   - 确立 Artemis Controller 与 Device Agent 的长连接协议契约（含 `PublishTaskDirective` 与 `ExecutionReceipt` 的完整 Schema 及错误码定义）。
