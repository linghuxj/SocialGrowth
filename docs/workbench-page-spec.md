### 运营账号管理（R-155）

提供最小账号管理页面，已有有效运营均可进入；列表显示人员标识、登录账号及启用／停用状态，支持开通与停用其他运营账号。开通不默认创建新的权限角色，凭据交付方式在身份契约中落实；列表不展示密码。停用前明确目标，提交后依据服务端结果更新，响应丢失时核对原请求；历史操作保留原人员归属，旧登录会话不能继续访问运营功能。

页面组织可放在必要设置入口，具体导航位置随实现落实。按 R-156，停用只处理访问权限，页面不增加负责人转移、项目暂停或交接向导；未完事项继续在原全局待办供其他运营代办，历史及原责任人保留，确需调整沿用既有编辑；避免停用最后一个有效运营账号的并发保护随身份契约落实。本节为页面职责草案，尚未实现。

## 2. 工作台：并列查看与处理

已选[原稿](design/workbench/home-selected-original.png)，后续[修订稿](design/workbench/home-refined-v1.png)保留并列结构。图片均为示例，字段含义以本文为准。

### 待办队列

每项显示事项标题、项目、需要处理的原因、受影响对象、负责人及事实更新时间；具体有效窗口临近时显示时间依据。紧迫性由已知期限和实际业务影响支持，不因同一错误文字自动升级或合并。

默认范围为全部项目；筛选“我负责的”按项目负责人，不按权限或是否曾点击处理。列表分清需要行动与等待复核的跟进事项；同项目同次故障聚合为一条待办，各任务的结果和恢复条件仍独立。

### 右侧详情

按问题与当前状态、影响及依据、人工所需动作、处理反馈组织。显示对应项目、Page/频道、手机及最后核对时间；原因较复杂时展开操作记录和证据。实际处理人另行记录，不能以项目负责人替代。

选中事项不改变业务状态；从邮件或任务深链进入时选中对应事项。事项已由他人处理时仍展示最新记录及结果，不展示空白错误，也不沿用过时按钮。

| 用户操作 | 页面立即反馈 | 后续反馈及边界 |
| --- | --- | --- |
| 点击待办 | 选中高亮、加载详情，明确当前对象 | 不自动接管、认领或解除暂停 |
| 切换待办或项目 | 已保存资料可直接切换；未保存时提供继续编辑、保存或放弃输入的明确选择 | 保存失败保留原输入；后端事实变化时重新核对 |
| 申请接管 | 显示请求已受理或失败，保留当前控制情况 | 取得独占控制后才允许操作手机；请求超时不视为成功 |
| 交还手机 | 显示交还请求及实际控制状态 | 交还不等于业务恢复；连接中断不自动认为已交还 |
| 提交处理结果 | 显示提交结果及等待复核 | 分任务显示恢复或仍受阻；不能直接关闭所有关联任务 |
| 新紧急事项出现 | 在队列提供可见提示 | 不把当前操作对象自动替换，不因列表重排造成误点 |

关闭页面不等于交还手机。重新进入时依据真实控制状态恢复展示；其他运营可代办，但不能同时取得同一手机的操作权。非手机表单也需核对是否已被别人更新，不能静默覆盖。

## 3. 项目筹备与设置

### 3.1 新建与返回项目

沿用 UI-005，先建立项目，再按实际资料到位顺序准备。新建时收集名称、公司自营/客户代运营、关联客户及负责人等识别信息；具体必填范围按业务输入落实，不强制将内容、手机、目标参数一次填完。创建保存成功即有可返回的筹备项目，未完成资料继续保留，不表示已开始执行。

项目列表区分筹备、运行、暂停与收尾等事实，显示需处理事项和负责人。点击筹备项目进入准备清单；运行后概览优先呈现当前目标、待办和进展，清单仍可追溯，不要求运营每天重新勾选。代表稿见[准备清单](design/workbench/project-readiness-v1.png)、[方向确认](design/workbench/project-direction-v1.png)及[周期设置](design/workbench/project-settings-v1.png)。前两张是新的虚构筹备项目“短剧出海·二期”，设置图是已有运行项目“短剧出海”，不是把同一项目运行状态重置。

### 3.2 可分批完成的准备清单

每项按“当前事实→缺什么→影响范围→处理入口”组织，不使用可以手工勾成通过的总清单或笼统百分比。资料已保存、检查通过、方向已确认、设备就绪分别记录；检查结果保留时间和适用版本，资料变更后旧结论不能自动沿用。

| 准备事项 | 要形成的事实 | 缺失影响与可继续工作 |
| --- | --- | --- |
| 目标与自主范围 | 阶段目标、受众、成品规则、身份范围、频率/窗口及方向版本 | 方向未确认不启动发布；可保存草案、补资料及推进独立资源准备 |
| 素材与业务资料 | 人工业务关联、来源、语言/版本/剧序、检查结果 | 缺项仅阻断相关素材；资料检查通过还须符合已批准规则才成为候选 |
| 发布身份与手机 | 项目专用分配、初始化、实际身份与执行能力 | 每个身份和手机分别判断，不因 YT 未就绪直接否定 FB 的资源条件 |
| 引流入口 | 现成承接入口、关联及平台有效引流路径依据 | 填入 URL 不等于路径有效，也不计入引流完成数 |
| 周期与运行规则 | 业务时区、首次起点、间隔、最低要求、观察及执行条件 | 未定值保留缺失与影响，不让 Demo 参数代填；按实际依赖检查就绪 |
| 负责人及提醒 | 责任人和提醒邮箱等已保存配置、通知实际结果 | 不将邮箱保存当成送达或处理；负责人不是独占操作权限 |

从每行进入对应素材、资源或设置页，返回保留项目、清单位置和输入。初始化等准备按自身授权与同机互斥进行，不因其他项未填完而全局锁死；也不能借准备步骤启动尚未批准的发布。引流最低要求应在计划阶段有足额且符合条件的安排，不能把尚未核实的入口当作完成准备或因资源不足自动降低要求。

独立检查失败显示原因、检查范围和重试条件，保留已成功项；刷新只读取现有事实，不重新分配资源、登录或派发业务任务。清单未齐不直接等于所有任务永久阻断；确认后按具体批准范围、计划要求和任务条件判断可执行性，不能仅凭某张清单行绿色就放行。

### 3.3 初始方向确认与自主执行

**首次进入自主运营沿用 R-017。** 运营设定目标和约束、确认 AI 初始方向后，满足就绪条件的任务可在批准范围内自动执行，不再增加独立“启动项目”审批或日常逐条批准。确认页必须在按钮附近清楚说明这一后果。

确认摘要至少包含项目与方向版本、账号阶段及主目标、受众、适用素材规则、FB Page/YT 频道范围、允许发布形式、有效日期/时段及频率、引流周期要求、影响判断的观察与数据条件、AI 可自主调整事项和必须再次确认的边界。完整规则应就近展开查看；重要限额不能只藏在链接中。来源与未决条件可追溯，不把 AI 生成文字自动当成已批准配置。

需分清两类未完成：

- **范围本身尚不明确**：目标、执行边界或其他必需批准内容缺失/冲突时，允许保存草案，不能把空值当不限或将其一并确认。显示具体待补字段，定位到修改入口。
- **范围已明确但准备未就绪**：可确认明确的方向与范围，同时保留初始化、入口核验或素材等阻断。后续就绪条件满足后可按该批准自主推进，不要求为每次补齐再次点启动；范围发生变化则按变更规则处理。

| 动作/状态 | 立即反馈 | 业务意义 |
| --- | --- | --- |
| 保存草案 | 资料已保存，仍待确认；保存失败保留输入 | 不能启动发布或扩大既有批准范围 |
| 查看方向 | 展示具体版本、依据、边界及未就绪事项 | 读取不确认、不重复生成新批准 |
| 确认方向 | 先核对当前版本；成功后显示确认人、时间和具体范围 | 就绪任务可以自主执行，未就绪仍受阻 |
| 确认结果暂未知 | 显示提交结果待确认，读取原请求/版本事实 | 不因浏览器超时再次生成批准或任务 |
| 确认后尚无可执行任务 | 方向已确认，列出仍缺条件或等待排期 | 不是确认失败，也不等于已发布 |
| 已开始自主运营 | 展示关联安排和执行进展 | 执行与平台发布核验继续分别呈现 |

按钮使用“确认方向”，不把“保存并退出”暗中等同批准。确认前若资料、范围或资源分配被其他人改动，展示差异并重新核对受影响内容，不确认用户未读的新版本。再次点击或重进页面只回到已有记录，不重复批准。已批准但暂停、撤权、退出或其他受阻的任务不能因清单补齐而绕过约束。

### 3.4 设置分组与保存范围

设置按日常操作目的分组；常用业务参数清楚可读，技术诊断细节不占据主表单。建议每组独立保存，并在按钮说明本次作用范围，不能一次保存静默提交其他标签页草稿。

| 分组 | 内容 | 保存/生效提示 |
| --- | --- | --- |
| 目标与范围 | 分阶段目标、受众、素材规则、身份及允许执行边界 | 草案与已批准版本并存；改变主目标/方向或越界须确认具体变更 |
| 周期与观察 | 首次统计起点、复盘间隔、时区、引流要求、指标观察窗口及收尾观察 | 周期/时区运行中变更按 R-132 下周期生效；其他字段单独说明影响，不能推定一律即时或下周期 |
| 执行规则 | 发布频率/有效窗口、并发与排队、自动恢复限制等已确认配置能力 | 不将硬约束变成普通开关；任务仍逐项校验，未知发布不能因恢复额度变更而重发 |
| 负责人及提醒 | 责任人、邮箱及实际支持的提醒配置 | 保存的是配置，不声称已发送或已处理；不新增人员权限隔离 |

已有默认值明确标“默认建议/当前采用值”，实际采用可追溯：复盘默认 7 天、效果默认每天尝试更新、同任务一轮自动恢复最多 2 次且累计最多 5 分钟（任一先到即按规则处理）。这些不是实测效果承诺；引流最低数、观察长度、收尾期限、实际国家语言等无统一已定值的字段不预填示例。并发数不绕过同机互斥。

阶段正式开通且存在批准目标时按 R-131 自动切换并留证据，不以打开设置页或重复确认代替平台事实；无批准目标或证据异常再交运营。目标与方向变更的摘要显示前后差异、对象、适用边界和生效条件；新草案不静默覆盖当前有效范围，也不取消仍有效的原安排。已开始或提交未知的任务不被普通编辑重新派发。

### 3.5 运行中周期与时区变更

按 R-132，当前周期边界和最低要求保留原值；复盘间隔/时区从下一周期起点生效，该起点接续当前周期结束的同一实际时刻。首期运行后不任意修改首次统计起点、不增加过渡周期、不产生空档或重叠。

保存前并列显示当前有效值、拟修改值、当前周期、待生效时刻（旧/新时区对照）、下一周期范围及受影响安排。日期必须完整且注明时区与结束不含；不能仅将旧日期标签换成新时区。界面建议使用明确时区名称，涉及夏令时或不可唯一解释的当地时间时显示实际偏移和待核对信息，不能擅自选择一个不同的实际时刻。

图稿示例：当前周期 2026-09-27 00:00 至 2026-10-04 00:00，Asia/Shanghai；拟把 7 天改为 14 天、时区改为 Asia/Bangkok。下一起点为 2026-10-04 00:00 +08:00，即 2026-10-03 23:00 +07:00，下一周期到 2026-10-17 23:00 +07:00 结束。这只是显示口径示例，不是实际改配置，14 天不是新默认。

本次表单只修改间隔和时区，不修改引流最低要求：现有 6 项示例值不因间隔翻倍而自动变为 12 项，也不能回写当前周期。若另需改最低要求，单独展示拟变更及适用周期，保留已经固定的当前要求；不能用修改周期规避当前缺口。

成功保存后显示“已保存，待下周期生效”、待生效配置与准确时间，当前值继续显示；到生效点读取实际生效记录后才显示新版本已生效。跨边界未开始安排重新核对批准范围、素材、有效窗口及依赖，不因为显示日期跨天而丢失、重复、补发或扩权；历史报告与待核实发布继续保留原口径和实际归属依据。

若提交时已跨过原预览生效点，重新读取当前周期并呈现新的生效范围，不能静默套用已过期的预览。已有待生效修改时显示具体版本与差异；再次修改不得创建互相冲突的待生效配置，更不能覆盖他人未被核对的变化。

### 3.6 异常、输入保护与验证

未保存状态在当前组可见，切换组或离开时保留草稿或明确选择继续编辑/保存/放弃；“放弃本次修改”只丢弃当前未保存输入，不撤销已批准方向或已保存的待生效配置。无修改时不产生新的版本或业务动作。

保存/检查局部失败保留输入和已完成事实；来源记录改变则标明旧检查失效，不静默强行通过。负责人更换不赋予或收回操作权限，不把提醒邮箱格式正确说成发送成功。未就绪、检查中、失败和事实未知使用清楚文案，正常筹备缺项不全用红色告警。

后续 Playwright 从真实 Web 新建并保存筹备项目，分批填资料、进入检查与返回，核对草案保存不启动发布；确认明确方向后检查批准记录和就绪/受阻任务分离，不能通过预置成功结果替代。运行中修改间隔/时区时验证当前周期不变、待生效版本、跨边界和并发变化、历史归属及重复操作不重复执行。真正进入自主执行与手机发布另需实际环境、授权和 Artemis 证据，静态确认按钮不代表本次已获发布授权。

## 4. 素材批量整理

项目名称在上传与编辑区域保持可见。批量表格服务人工整理，未承诺导入 Excel、自动识别视频或自动推断集序。

| 字段组 | 内容 | 交互建议 |
| --- | --- | --- |
| 文件与身份 | 文件、预览、内容名称/标识、成品类型 | 上传与资料检查分开；同名文件不能自动合并 |
| 业务关联 | 商品或短剧、基本内容说明与事实 | 可批量填写共同字段；不能由 AI 补造事实 |
| 语言与版本 | 语言、视频语言版本组、文件版本关系 | 人工确认，显示现有关系与冲突，不凭文件名自动关联 |
| 短剧关系 | 集序、连续剧集或独立宣传片 | 仅适用内容填写；不按排序静默编号 |
| 来源与准入 | 来源声明及证明、首次未发布声明、重复检查与疑点 | 声明与已有记录共同判断，缺少历史不能证明未发布 |
| 检查及分发进展 | 上传结果、待补字段、准入结果、平台名额及关联安排 | 不把“可供安排”显示为“将发布”或“已成功” |

选中行后显示本次操作数量与字段，批量补空值和覆盖旧值分别表达。保存返回逐项结果，失败项保留输入并定位原因。用户可只筛选待补项、展开预览核对再返回原位置；无关合格内容不等待整批完成。

素材更正进入版本与影响摘要，列出受影响未提交任务及已提交/未知事项；正式撤回与平台已发布内容撤下分别提供入口，不能用一个删除按钮涵盖三者。具体平台撤下仍需明确平台、发布身份、内容与操作。

### 4.1 素材页布局与操作顺序

本轮根据 UI-006、UI-009、UI-011 细化为三张关联状态稿：[批量列表](design/workbench/materials-batch-v1.png)、[批量填写](design/workbench/materials-bulk-dialog-v1.png)、[单条预览编辑](design/workbench/materials-preview-v1.png)。它们是同一方案的不同状态，不是三种待选风格；具体细节仍为设计建议，未新增用户确认编号。图稿说明、提示词与检查局限见[视觉稿索引](design/workbench/README.md)。

顶部持续显示项目名称和项目内导航，素材页提供上传、状态筛选与搜索。表格优先呈现人工需要核对的关联字段；来源、长说明及完整版本关系放在单条详情，避免将全部业务资料挤进主表。素材属于商品展示时使用对应商品字段，不强制出现短剧集序。

主路径：在当前项目上传成品 → 查看上传及缺项 → 选择相关行 → 批量填写共同字段并检查变更预览 → 应用到表格待保存区 → 必要时打开单条预览核对 → 保存 → 查看逐项保存和检查结果。选择多行不代表已经修改，应用到表格不代表已经持久保存，保存资料不代表准入或发布。

### 4.2 选择范围与批量填写

- 勾选只确定批量操作对象；表头选择框部分选中时必须呈现不确定状态，选中数量与行状态保持一致。首期建议表头仅选当前页可操作行，不隐式选择跨页或被筛选隐藏的记录。
- 筛选、翻页后显式重建选择范围，提示原选择已清除；已编辑但未保存的数据单独保留，不因取消选择而丢失。切换项目前处理未保存输入，不将上一项目的批量范围带入新项目。
- 上传失败的文件保留记录并提供“重试上传”，不参与依赖文件的内容准入操作；重传同一文件关联原记录，不冒充重新导入一份新内容。重传时发现文件不一致，应按更正/重新核对处理。
- 批量填写弹窗显示项目、选中数量、字段和值，默认建议“仅填空值”；明确选择覆盖时才替换已有内容。无论哪种，都逐项展示旧值→拟填值，以及跳过或不可操作的对象。
- 点击“应用到表格”只更新待保存资料，行上标明“未保存”。未改任何有效字段时不产生新变更；不靠重复点击重复创建内容或版本。
- 语言、内容类型及共同业务归属可按人工选择批量填写。集序、内容身份及版本关系需要逐项明确对应；不能把同一值简单复制给所有剧集，也不自动用文件名或排列顺序推断。

### 4.3 单条预览与编辑

点击“预览”打开对应素材详情，保留列表筛选与位置。足够宽时采用右侧覆盖详情，避免把主表压缩到不可读；窄桌面窗口可切换完整详情页。图片或视频预览失败时说明文件状态和原因，不将无法预览视为准入通过，仍保留可核对资料。

详情明确项目、文件标识及保存状态，按内容类型显示商品/短剧、语言、集序、版本关联、内容说明与事实、来源声明和证明。视频画面仅用于人工核对，不能将设计稿示例画面或自动识别结果当作已确认业务事实。

文件版本用于识别当前文件，应只读；更换文件须走更正流程，不用普通下拉框覆盖历史。版本组的可选对象需能展开查看关联内容，不只依赖类似 E03 的简称；剧集、语言版本和文件修订分别表达。

“保存本条”仅提交当前素材的待保存变更，其他素材修改保留；保存成功后显示对应检查进展，不能直接变成发布成功。关闭详情、返回列表或切换对象时，有未保存修改则提供保留草稿返回、保存后返回及放弃本条修改的明确选择，保存失败留在当前上下文并保留输入。保留草稿仅指当前工作会话，未承诺浏览器关闭后或跨设备同步恢复。

### 4.4 保存、准入与部分失败

页面“保存资料”提交当前项目内所有未保存修改，明确显示数量和涉及对象，不以勾选状态暗示保存范围；若部分修改被筛选隐藏，也须可展开查看再提交。“保存本条”则只提交一项。按钮文案与摘要需要同时说明实际范围，不能只因当前选中两行就默默遗漏其他修改。

| 状态/事件 | 用户应看到的反馈 | 后续动作 |
| --- | --- | --- |
| 有未保存修改 | 行标记、待保存总数，能定位具体字段 | 保存、继续编辑或放弃明确范围 |
| 正在保存 | 本次提交对象及进度，避免重复提交同一变更 | 保留输入；后续编辑不能被较早保存结果覆盖 |
| 部分保存失败 | 哪些已保存，哪些未保存及原因 | 保留失败输入，仅重试仍需要保存的变更 |
| 保存结果不明 | 显示“保存结果待确认”并核对最新资料 | 先读取事实，不当成失败重复创建记录/版本 |
| 资料保存成功 | 已保存的具体资料及对应版本 | 展示规则检查中或实际检查结果 |
| 检查仍有缺项或疑点 | 定位缺项、冲突或人工核对事项 | 继续补齐；不将其他合格素材一并阻断 |
| 检查通过且符合范围 | “可供安排”并说明由 AI 选择 | 不新增逐批审批，不保证一定安排或立即发布 |
| 内容被他人更改 | 当前保存值、本人拟改值及受影响字段 | 保留本人输入，重新核对后再保存，不静默覆盖 |

来源材料“已填写”与“已核对”分开显示，不能用绿色通过标记替代事实核验。统计筛选基于实际保存及检查状态；未保存的新语言值不让“可供安排”数量提前增加。

示例用于设计推演：列表有 6 项，2 项可供安排、3 项待补充、1 项上传失败。运营只修改第 3、4 项语言；若第 3 项保存成功、第 4 项因并发修改失败，反馈为“已保存 1 项，1 项未保存”，第 3 项还需检查，第 4 项保留输入，其他记录不改动。这不是测试结果或实际业务数据。

### 4.5 已有素材更正与新内容整理的区别

本轮图稿展示首次成品整理。已有候选或已有发布安排的内容发生文件/业务事实更正时，普通保存入口应引导到更正摘要，展示旧值、新值及受影响任务，保留版本和记录；不能让“批量覆盖”绕过暂停、核实与重新检查要求。

已经发布的内容不能通过重新上传或改版本组获得新名额。素材正式撤回后重新使用仍须重新核准，单纯补齐字段不会解除撤回。平台内容撤下单独确认，不放在批量填写或上传失败清理的默认操作中。

### 4.6 素材页后续验收场景

1. 实际 Web 上传多份文件并人工填写关联，部分失败只重试对应上传；现有成功记录和资料保持可追溯。
2. 选择两项空语言字段，应用共同值后仍显示未保存，保存及检查前不增加候选数量；已有其他语言值在“仅填空值”模式下保持原值。
3. 单条预览编辑与页面保存范围清楚，取消选择、筛选及返回不静默丢失输入；关闭会话不虚构草稿已永久保存。
4. 两名运营同时修改一项资料，后提交者看见真实冲突，失败输入保留且已保存项不重复创建。
5. 通过实际支持的失败条件检查逐项保存反馈；不能预置成功状态或 Mock 准入结果证明闭环通过。
6. 更正已有安排的素材后，仅受影响任务按事实重新检查；已提交或未知结果先核实，不因修改成功而自动重发。

以上为未来 Playwright 页面验收与必要业务证据要求，本轮仅完成静态设计及文档核对。

## 5. 发布安排与任务详情

执行列表以一条平台发布任务为一条记录。FB/YT 分别显示，重排、恢复或版本更正沿用原任务关联；未选用的候选素材不放成虚假排期。

默认列建议为内容摘要、语言/版本、平台形式、Page/频道、计划时间、执行进展、结果核验及关注原因。筛选包含日期及日期口径、平台、状态；计划时间与实际发布时间不能混用，没有时间的记录需可查。

任务详情展示当前事实、文件准备情况、发布信息、发布身份及手机、策略和批准依据、安排变更、提交及核验证据、相关待办与后续效果。手机日志、连接参数等技术信息收进必要诊断区域，不占据业务摘要。

执行中、已提交、结果待核实与核验成功分别表达。没有效果数据不改变已核验发布事实；未知结果不出现普通“重发”动作。连载依赖等待说明前置剧集和平台，FB 受阻不自动阻断 YT。

### 5.1 三张关联状态稿与范围

本轮新增[发布列表](design/workbench/publication-list-v1.png)、[待核实详情](design/workbench/publication-pending-v1.png)、[核验成功详情](design/workbench/publication-verified-v1.png)，沿用 UI-007、UI-009、UI-011 和现有发布核验要求。三图为设计建议，不增加逐条人工审批，也不把所有待核实任务都转人工。

两张详情使用同一示例任务 PUB-YT-003：自动核验缺少证据时需要人工协助，处理结果提交后继续复核，最终取得匹配的发布事实。图中成功是预设的视觉场景，不表示通过生成图片或人工点击即可将真实任务改为成功。图稿与提示词、待修正项见[视觉稿索引](design/workbench/README.md)。

### 5.2 列表筛选、时间与计数

列表按任务展示，内容、平台形式及发布身份共同帮助辨识。只看同名标题不足以确定任务，详情应保留稳定的任务关联、素材及语言/文件版本。Shorts 与常规视频仍属于同一平台名额规则。

日期筛选须明确按计划时间或有证据的实际发布时间；缺少对应时间的任务不能偷偷算入某天。提供独立“未排期”或“实际时间未知”入口；如果支持同时查看，必须显式显示“包含未排期/未知时间”的范围，而不是仅显示某一天却混入无时间记录。

计划时间、实际发布时间、核验时间与最近更新时间分别显示。列表可用较短格式，详情补足日期和时区；跨时区查看必须保持实际时刻一致，不能简单替换标签。刷新时间不能替代平台事实时间。

一项发布任务的重排、恢复、回执补齐或核验更新不增加任务行数与发布完成数，历史安排收进变更记录。尚未被 AI 选用的素材仍留在候选内容，不伪造为待发布任务。已取消任务可查历史，不与当前有效安排混淆。

### 5.3 执行、结果与效果分开表达

以下是展示语义示例，不锁定最终数据库枚举；多维事实可能同时存在，不能将所有状态塞进一条必然线性进度条。

| 当前事实 | 执行进展 | 发布核验 | 效果/后续反馈 |
| --- | --- | --- | --- |
| 尚未到可执行条件 | 已排期、文件准备中或等待前置，并显示具体原因 | 尚未开始核验 | 等待发布，不能记零 |
| 手机进入平台发布流程 | 执行中，明确最后已知步骤 | 尚未确认平台发布 | 不因执行中就计算效果 |
| 有提交动作记录但缺平台证据 | 提交动作已记录；平台是否接收按实际已知事实说明 | 结果待核实 | 等待发布核验；不是发布失败 |
| 提交本身也无法确认 | 提交状态未知，保留最后操作证据 | 结果待核实 | 先核实，不能按未提交直接重发或取消 |
| 正确身份与内容已有充分证据 | 保留原提交及执行记录 | 发布成功 | 数据可待采集、缺失或观察中，均不撤销发布事实 |
| 核验发现身份或内容不符 | 如实保留实际操作 | 异常待处理，说明差异 | 按实际影响暂停，不自动另发一份或删除已有内容 |

“发布成功”与“实际发布时间已确认”也可分开。身份和内容证据充分但精确时间未知时，保留已核验发布事实，周期归属及依赖实际时间的评价待确认，不能用计划时间推算。后续发生删除、限制或不可见等平台变化时记录新的事实，不抹去原核验历史。

### 5.4 详情阅读顺序与证据内容

详情从发布列表、首页待办或相关素材深链进入，持续显示项目、任务、平台形式与目标发布身份。返回时保留来源列表筛选及位置。

顶部先呈现执行进展、平台结果及效果可用性，再说明当前原因和所需行动。下方主要区域展示任务信息与时间线，旁侧或后续区域展示核验依据、缺口、人工协作和影响范围；窄桌面窗口可按阅读顺序排列，不硬挤双栏。

| 信息 | 应保留的内容 | 不应作出的推断 |
| --- | --- | --- |
| 任务目标 | 项目、FB Page/YT 频道、内容身份、语言及文件版本、执行手机 | 已分配的目标身份不等于平台实际发布身份已核对 |
| 文件准备 | 任务对应文件、传送完整性、手机端可用及实际选取的核对依据 | 文件已传送不等于已进入发布或发布成功 |
| 批准与安排 | 阶段目标、适用批准范围、前置依赖、有效窗口、文案及安排变更 | AI 解释本身不代替批准记录，也不放宽硬约束 |
| 发布事实 | 平台实际身份及内容的匹配依据、核对渠道及时间、证据记录 | 上传/提交提示、标题相同或最新一条内容不足以独立证明成功 |
| 平台标识或链接 | 可取得时保存并关联原任务；无法取得时说明 | 缺链接不直接等于发布失败，也不允许凭空补造标识 |
| 实际发布时间 | 来源支持的时间、时区及精度；未知或仅有范围则如实显示 | 不用计划时间、核验时间或估计分钟冒充实际时间 |
| 效果记录 | 对应已核验发布的来源、覆盖区间、统计截止、采集时间、归因层级 | 缺数据不当零，账号数据不强分配到单条内容 |

身份与内容匹配的充分证据是核心，图稿中的四项证据行不是要求每个字段都有值才可成功的硬性勾选清单。实际能够取得哪些证据，仍按平台能力与可用渠道验证。

时间线区分事件实际发生时间与记录收到时间；迟到记录保留关联。页面可折叠较早记录但不能覆盖旧事实；中心重连、更换 AI 会话或重复消息不能创建新的发布事实。远程查看画面显示更新时间和是否实时，不将旧截图当作当前设备状态。

### 5.5 待核实到人工协作

系统可在已批准渠道和有效授权内继续自动核验时，页面显示核验进展及最近尝试，不要求运营例行“确认成功”。确需人工的事项才出现“处理核实待办”，链接到原关联待办；无待办时不因打开详情而自动创建。

人工协助先查看已知事实及缺口，按需要提供实际观察、证据来源、关联平台内容及可确认的时间等处理信息。普通说明不收集账号密码、验证码或令牌。若要操作手机，进入既有申请接管→获得独占控制→操作→交还→恢复复核流程；打开待办不是接管许可。

| 操作/事件 | 当下反馈 | 不可越过的边界 |
| --- | --- | --- |
| 刷新详情 | 正在读取最新事实，保留上次更新时间 | 只是读取，不重复派发发布或核验业务任务 |
| 打开核实待办 | 当前待办、处理情况、受影响任务及证据缺口 | 不重建相同待办，不自动取得手机控制 |
| 提交人工处理结果 | 已提交或提交失败，保留实际处理人及内容 | 待复核不是发布成功；失败保留输入 |
| 人工或系统发现内容已经发布 | 复核与原任务的身份、内容对应关系 | 不另建一次发布、不再次消耗名额、不重复计数 |
| 证据不足或互相冲突 | 仍待核实、明确缺失/冲突及下一步 | 不因等待时间长、项目结束或窗口已过直接判失败 |
| 发布核验成功 | 保留证据、核验时间和实际发布事实 | 不代表设备已恢复、后续任务已执行或效果达标 |

提供者暂停手机时不能借核验继续操作该手机；可用其他获准渠道核实，需该手机的工作等待有效授权下恢复复核。离线或撤权不表示停止已确认，更不授权强行接管。

### 5.6 连载、周期与后续效果

本集核验成功只满足同平台后续依赖剧集的一项前置条件。后续仍须检查批准范围、素材、手机、授权、有效窗口及其他暂停；不能把“前置满足”直接写为“下一集已发布”。FB 与 YT 分别判断，资源共享故障按实际影响处理。

迟到核验按有证据的实际发布时间归属原周期，保留原报告及更正，不重复计入核验当天的新周期。例：09:30 排期、09:35 实际发布、10:12 完成核验应显示三个时间；这只是设计示例，不规定平台能提供这样的精度。

发布成功后页面链接到该内容的效果记录；数据暂缺时显示待采集或不足，不显示虚构的零播放或零收益。数据已取得但观察窗口未满时保留观察状态，不展示无依据的改善结论。资源交接后，原发布的项目和身份关联继续保留。

### 5.7 页面异常与后续验收

- 从旧提醒进入时已核验成功：展示当前结果和历史待办，不保留过时的重试或重复处理入口。
- 核验中页面刷新或连接中断：恢复读取同一任务事实，保留未知部分，不因页面重进而再发一次发布。
- 项目已暂停/结束：页面仍可阅读、追溯并按授权核实未决事实，不能借核验入口启动新的发布。
- 证据链接不可访问：保留原核验记录，说明当前证据读取失败并尝试补充，不凭单一链接错误改判发布失败。
- 来源时间或身份矛盾：明确冲突及受影响判断，保留历史，不让最新收到的一条记录无条件覆盖已确认事实。

后续 Playwright 验收须从真实 Web 查看任务、进入对应待办并提交实际人工反馈，断言操作与状态按上述关系更新；设备操作及平台事实由 Artemis 与实际证据支撑。应特别覆盖：执行结束但尚未核验、提交状态未知、无平台链接但有其他充分证据、发布时间未知而归属待确认、重复回执不重复计数、后续剧集仍有独立阻断等场景。静态成功稿不能充当其中任何一项通过证据。

## 6. 效果与复盘

### 6.1 页面职责与阅读顺序

对应 UI-008：先回答目标推进到哪里、什么阻碍判断、下一步实际做了什么，再下钻指标。周期总览与复盘详情不是两个新的全局导航入口，均位于项目内的“效果与复盘”。代表稿见[周期总览](design/workbench/effects-overview-v1.png)和[复盘与落实](design/workbench/review-followthrough-v1.png)，属于设计建议，不代表真实效果或执行证据。

| 阅读层次 | 运营需要得到的答案 | 进入下一层的操作 |
| --- | --- | --- |
| 查看范围 | 哪个项目、哪个周期、什么目标与评价口径 | 选择已有周期、查看历史报告与周期配置 |
| 目标进展与缺口 | 完成多少、缺口多少、哪些事实仍待核实 | 查看对应任务，保留周期与计数筛选 |
| 账号阶段 | 哪些 Page/频道处于什么阶段，依据与生效时间是什么 | 查看该身份的阶段证据与适用批准目标 |
| 本轮判断与行动 | 维持或调整的依据、局限、是否需要运营处理 | 打开复盘详情或既有确认待办 |
| 实际落实 | 哪些安排已更新、执行/核验到了哪里、新反馈够不够 | 查看关联任务、阻断、效果证据 |
| 指标明细 | 来源、时间、归因及比较是否可靠 | 查看指标详情、原记录与更正关系 |

页面更新时间不等于所有指标的数据截止。首屏保留关键缺失及其影响，其他说明可展开；不靠装饰性趋势图、综合健康分或单一“复盘完成”状态代替上述事实。

### 6.2 周期、目标与计数

周期选择只切换查看范围，不修改业务时区、周期边界或最低要求。以项目业务时区完整显示起止日期时间，采用起点包含、终点不包含的明确表达；时区在本页只读。运行中配置修改经设置入口展示下周期生效点，当前与历史口径保持原值，按 R-132 连续衔接，不允许通过任意拖动日期重写周期。

默认查看当前周期，标明进行中和首次/下次复盘到期时间；历史周期明确已结束。图稿选中的是已结束周期，后续落实跟踪从该周期结束后展开，单独标示跟踪截止，不能把后续新增任务或指标静默混进原周期总计。进入历史报告时还须分清报告生成时快照与后来更正/最新跟踪。

引流任务区域显示最低要求、计划安排、核验成功、失败、待核实及缺口。缺口按 `max(最低要求－符合该周期计数条件的核验成功数, 0)` 计算；当前周期称“距最低要求还差”，周期结束后称“周期缺口”。超额完成如实保留，不把进度条封顶后的数字当真实完成数。

计数须同时满足有效引流路径、原任务关联及有证据的周期归属；同内容 FB/YT 可分别计数，同任务恢复、重排、版本变化或重复回执不增加数量。计划是安排口径，不是成功量，也不要求永远等于成功、失败和待核实之和：未开始、执行中、取消、移出周期等按实际状态另列，跨周期调整保留关系。周期归属待确认的发布单列，不凭排期算入已完成；已安排在该周期的未决事项仍可出现在原计划追踪中，但不能暗示其实际发布时间已知。

示例最低 6、计划 6、成功 4、待核实 1、失败 1、缺口 2 仅用于读图；没有新增默认最低值，也不保证真实项目只有这些状态。点击缺口展示缺口计算和有关任务，不虚构“两条缺口任务”以凑数。历史缺口用于分析原因，不自动累加下期最低要求。

各发布身份分别显示阶段、阶段主目标及批准版本。数值达标/申请中不能显示为正式开通；正式开通已核验且有批准目标时按 R-131 自动切换并保留生效记录，异常进入原协作流程。查看旧周期须显示当时适用目标，周期内切换应可追溯，不能用当前阶段改写历史或当前最低要求。广告收益预估、实际到账与分佣数据分别表达，不把指标缺失渲染成零收入。

### 6.3 指标下钻与可比较性

点击指标行打开详情面板，保留项目、周期、身份/内容筛选与返回位置。面板至少展示指标定义与单位、来源渠道、对应项目与发布身份、内容/原任务关联是否成立、实际统计区间、来源时区、统计截止、采集时间、观察窗口及归因层级；不能取得的字段直接标未知。查看原始依据遵循授权并脱敏，不暴露凭据。

| 数据情况 | 应显示的反馈 | 对判断与行动的影响 |
| --- | --- | --- |
| 已取得真实零值 | 0，并保留来源和区间 | 只在口径与证据可比时进入比较 |
| 尚未取得或采集失败 | 待采集/采集失败，最近成功记录及其截止 | 不当零、不重发内容，区分旧值与新尝试 |
| 观察窗口未满 | 已覆盖区间、窗口预计结束及仍在观察 | 可以查看事实，暂不据此形成内容效果优劣结论 |
| 窗口已满但证据不足 | 缺什么、影响哪项判断、补齐进展 | 继续保留未知，不按到期自动转可比较 |
| 只有账号级点击 | 对应账号与范围，内容来源未知 | 不分摊到单条内容，不制作内容引流排名 |
| 累计指标多次采集 | 各快照与截止、当前有效记录 | 不将多次累计值相加当新增效果 |
| 平台统计日与项目日不同 | 保留来源实际区间与时区 | 无法可靠拆分时不冒充项目日汇总 |
| 已更正或补齐 | 前后值、依据、受影响结论与更正时间 | 原报告可查，不静默覆盖，也不重复计数 |

点击采用当前已确认定义：排除已识别预览请求和重复记录后的点击，不等同真人、到达或成交。内容链接的配置关联不能替代真实来源归因。不同单位、币种、定义或不完整覆盖不可无条件合并成一个项目总数；覆盖不足的合计标明范围，不伪装完整总计。

内容比较须同时核对观察窗口结束、时长/定义/证据可比性。精确发布后窗口与完整平台统计日窗口分组展示；后者从发布后首个完整统计日起算，首个不足整日区间单独观察，保留实际区间及发布后偏移。同为三天或同样已结束不自动可比。具体窗口长度沿用项目配置，图稿不预设小时数或准入样本阈值。

主目标数据缺失时维持原批准范围内安排、尝试补齐，并明确暂停哪些依赖数据的优化；不能擅自改用更容易取得的指标替代主目标。正常发布、项目汇总和重大异常处理不因普通观察未满而全部停止。

### 6.4 从判断到实际落实

复盘详情固定显示复盘编号、所评周期、生成时间与报告版本，按“依据与局限→维持/调整理由→安排变化→实际执行→新反馈”阅读。每条结论须能到具体证据；每项行动须能到对应安排或不行动的依据，避免仅保存一段 AI 文本。

| 事实层次 | 展示内容 | 不等同于 |
| --- | --- | --- |
| 判断/建议已形成 | 原目标、使用的反馈、局限、拟调整或维持理由 | 已更新安排 |
| 安排已更新 | 原值→新值、生效时间、受影响对象、批准范围和版本关系 | 已经执行 |
| 实际执行 | 原任务状态、执行进展、平台核验结果与阻断 | 效果改善 |
| 新反馈已取得 | 对应实际发布、来源、窗口及可比较性 | 能确认调整导致改善 |
| 继续观察/维持 | 证据不足或无须调整的原因、后续观察安排 | 闭环失败或必须另造一项变更 |

范围内调整无需逐条审批，直接展示已发生的变更。改变主目标、已确认方向或突破范围才关联人工确认待办，明确拟改范围、影响、依据、原范围与生效条件；未确认不实施该变更，其他仍有效的批准安排按条件继续。确认的只是展示的具体变化，不扩大内容撤下、资源交接或发布权限。

普通复盘只能保留、取消或重排尚未开始的任务；已经进入平台发布流程、已提交或结果未知的事项单独处置。更新安排时重新核对最新状态，不能拿复盘生成时的旧事实覆盖正在执行的任务；部分更新失败则逐项保留结果与原因。新版本生效后旧安排不得再次执行；查看记录、刷新、反复打开详情不重新应用调整。

后续任务受阻时，从该任务进入原待办或资源详情，保留具体阻断而不是将整份复盘标成失败。后续安排被另一轮复盘取代时展示替代关系及当前有效版本，保留曾经生效及已执行记录。未调整也可形成有依据的复盘，不强制每轮改变时段或内容。

### 6.5 两张图的关联示例与动作

示例 REV-0927-01 评价 09-20 00:00 至 09-27 00:00 的周期；页面在 09-27 12:00 查看。两账号资格进展数据未补齐，因此维持方向；基于手机可用时段，将两项当时尚未开始的后续任务在原有效窗口内重排。这是执行条件调整，不是从缺失效果数据推导出优化结论。

PUB-FB-005 从当天 09:00 改为 11:00，有效窗口 09:00–12:00，示例实际发布 11:03、核验 11:08，新效果待采集。PUB-YT-004 从 13:00 改为 15:00，有效窗口 13:00–17:00，前置第 3 集已核验，但手机仍待恢复复核。两者属于后续周期，不用于弥补上方原周期的缺口。与上一组图关联的 PUB-YT-003 在 09-27 发布，同样不能算进截至当天 00:00 的旧周期；其效果若在同页展示，必须单列“周期后跟踪”。全部时间仅为设计示例。

| 操作 | 页面结果与返回连续性 |
| --- | --- |
| 切换周期 | 更新所选周期目标、报告及口径；后续跟踪范围另标，保留身份筛选并说明无匹配项 |
| 查看任务计数 | 进入按计数条件筛选的任务明细；展示未纳入原因，返回保留周期 |
| 查看数据来源 | 展开指标或证据详情，展示历史快照与当前有效记录 |
| 查看复盘与落实 | 进入该复盘，不自动重新生成、确认或应用变更 |
| 查看任务/阻断 | 进入同一原任务或关联待办；不会重派发或解除暂停 |
| 查看历史报告 | 默认清楚标注所读版本，可对照原报告与更正依据 |
| 刷新 | 读取新事实并标注更新，不表示强制采集、发布或重新复盘 |

不增加“全部批准”“标记优化成功”或“一键重新发布”等捷径。独立聊天不是完成流程的前提。

### 6.6 更正、收尾及异常状态

- 迟到发布核验：按有证据的实际发布时间更正原周期，保留原报告、完成数/缺口变化与依据；未知时间则继续归属待确认，不计到核验当天的新周期。
- 后续证据改变结论：历史建议仍保留当时依据，展示新结论及其对尚未开始安排的影响；不能回写成“当时已经知道”。
- 无复盘报告：区分首轮未到期、正在形成、失败或无可用数据，展示已知目标和已有进展；不以空白页掩盖缺口，也不生成虚假结论。
- 局部采集失败：保留可用指标，逐项显示截止及失败原因；一个账号失败不能令其他已得数据变成未知，旧值也不能改标最新。
- 项目暂停发布：按权限与资源条件继续既定效果采集，不因新建议启动发布；提供者暂停手机时不借采集继续操作该手机。
- 项目正式结束：显示项目配置的收尾观察结束点、已得数据与缺失，期满形成收尾报告并停止常规采集，不触发新发布；未决发布仍独立核实。
- 多人或异步状态变化：只读事实可更新并提示；待确认变化的范围已失效时展示差异并重新核对，不静默扩大批准或覆盖新安排。

### 6.7 后续验证场景

后续 Playwright 从真实项目页面切换周期、下钻数据、查看变更和任务，并在实际需要时进入原人工待办处理，验证返回状态、口径和实际记录关联。重点覆盖零与未知、账号级归因不分摊、窗口未满/已满但缺数据、累计快照去重、迟到核验更正旧周期、下周期配置生效、范围内调整免审批、任务已开始后的并发冲突、部分更新失败、后续受阻及项目结束收尾。

任务安排与发布核验的通过不等于业务效果改善；效果结论另需真实数据及可比性证据。静态图、示例数值和上述候选场景均不是已执行测试，本轮未启动服务或执行发布。

## 7. 账号、设备及接管

### 7.1 资源列表与接管详情的职责

UI-014：用户最新选择恢复此前浅色设计稿，继续后续页面，不采用 UI-013 的 Demo 大屏视觉分支。账号与设备以[资源列表](design/workbench/devices-overview-v1.png)定位对象，必要时进入[人工接管详情](design/workbench/device-takeover-v1.png)；详情采用完整手机画面旁配置处理信息与明确动作的浅色结构，不再以深色多机大屏作为本轮主要设计。

原稿恢复为布局依据，不表示其中生成的频道名、订阅数或独占状态成为真实事实；正式页面仍显示实际回传与真实控制状态。此前制作的[大屏 HTML 预览](design/workbench/device-monitor-preview.html)、渲染和[回传盘点](design/workbench/device-monitor-data-mapping.md)保留为历史探索，不能继续作为当前视觉方案；其中关于时间、未知值、互斥与事实来源的核对原则仍适用。

| 视图 | 首要内容 | 适用操作 |
| --- | --- | --- |
| 发布身份 | FB Page/YT 频道、项目、当前执行手机、阶段证据、未决事项 | 查身份、初始化、换机与交接 |
| 设备/接管详情 | 实际回传的完整屏幕、当前操作方、处理范围、任务及记录 | 查看、放大、按需申请接管、提交处理与交还 |
| 资源列表 | 设备、提供者、项目、承接身份、连接/授权、控制方、执行条件 | 筛选核对、首次分配、查阻断与历史 |

资源列表按实际设备记录生成行，不为凑满界面复制同一手机或补示例设备。项目及状态筛选须明确范围；无匹配、确实无设备、尚未获得设备清单和读取失败是不同状态。历史离线记录不计入当前在线数，同一手机的多平台绑定和重复上报不能重复计为多台。

列表与选中对象尽量稳定；新事件更新对应对象，紧急事项提供可见提醒，不在点击瞬间重排导致误操作。设备多时按项目筛选并分页，详情可放大选定设备画面；具体同屏数量和刷新频率按实测性能、可读性与设备授权确定，不把 Demo 的三列/三秒写成要求。

### 7.2 发布身份与设备条件

账号视图以发布身份为核心，FB 登录账号作为受控关联信息，不能与 Page 混为一个字段；YT 显示频道。同一手机可关联 FB 与 YT 身份，但必须属于同一项目，日常同平台不轮换账号。列表中的已分配身份与手机当前实际识别身份分别表达，身份不符显示差异并转人工，不能用分配值替代观察结果。

| 条件 | 页面应显示 | 不得直接推断 |
| --- | --- | --- |
| 设备接入 | 提供者、支持条件检查、分配、初始化各自状态 | 注册成功即可以执行 |
| 管理连接 | 当前可达性、最后确认时间及异常范围 | 页面事件连接成功即每台手机在线 |
| 业务上网 | 已有检查结果及更新时间；未查则未知 | 管理连接可用即 FB/YT 也可用 |
| 授权 | 有效/失效/待核对及影响，必要现场协助 | 网络恢复即授权恢复 |
| 控制 | 当前实际操作方、申请/停止/交还进度 | 空闲、持有记录或请求已受理即取得控制 |
| 设备就绪 | 各项必要条件的复核结果 | 就绪即所有任务可以立即发布 |
| 单任务条件 | 批准范围、素材、身份、窗口、依赖和其他暂停 | 手机恢复即解除项目暂停或补发过期任务 |

同一提供者的每台手机独立准入、分配、暂停及恢复，不能因同属一人联动全部设备。首期稳定 Wi-Fi、原厂 Android 和实际支持范围等约束不因监控设计改变；不用固定 USB 文案要求分散部署现场增加电脑或网关。

### 7.3 真实画面、事件与时效

屏幕区域完整呈现实际回传图片或经过验证的视频能力，保持原比例，不裁掉顶部身份、底部按钮或弹窗，不用图像生成重绘平台内容。状态、步骤、身份匹配结论和操作按钮放在屏幕外，不能把产品 UI 盖在关键手机证据上。缩略图可以放大，放大只改变查看尺寸，不自动取得控制或发送点击。

卡片至少保留设备标识、实际任务/会话关联、步骤及动作摘要、平台和身份来源、连接状态、控制情况、画面/状态各自的时间及未知项。步骤没有总数就不画完成百分比；步骤完成不等于发布核验成功。没有回传的机型、网络类型、电量、信号、账号名不填固定默认值。

区分画面采集时间、状态事件发生时间、服务接收时间与页面读取时间。刷新页面或收到新的动作事件不能给旧图片换上新时间；图片没有独立采集依据则显示时间未知。只有实际证据支持的连续更新才可称实时画面，事件截图称“最近回传画面”；更新时间间隔不能冒充帧率或视频流能力。

| 场景 | 画面与状态展示 | 可用操作 |
| --- | --- | --- |
| 新状态到达，画面未更新 | 显示新步骤，同时保留旧画面时间与不同步说明 | 可查看记录；不能以旧画面安全操作 |
| 图片加载失败 | 显示读取失败；有旧图时标最后成功时间 | 重试读取该图，不改变任务或设备状态 |
| 无任何截图 | 显示尚未取得画面 | 在允许的授权与控制条件下请求截图；不能填模拟 App 画面 |
| 设备离线或控制失联 | 保留最后画面并明确过期/非实时；控制未知时禁止操作 | 可查历史，不确认停止、交还或恢复 |
| 只有历史资料 | 历史日期、来源及局限，当前条件未知 | 只读查看，不与当前设备数混算 |
| 敏感验证页面 | 受控显示或遮蔽，并说明画面受保护 | 不向普通日志、截图报告或模型上下文泄露密码/验证码/令牌 |

“刷新状态”读取已有事实，“重试读取图片”取已有图，“请求新截图”可能触及手机，三者分开。请求截图须服从暂停、授权与同机控制约束，不插队干扰正在进行的操作，也不能把任务状态改成 idle 或解除阻断。提供者暂停期间不借自动轮询、截图或核验继续操作该手机；可用其他获准渠道核实的按自身条件进行。

### 7.4 首次分配、换机与跨项目交接

首次接入依次呈现系统设备检查、运营确认项目与公司发布身份分配、AI 登录初始化及实际身份/能力核验。分配表单展示设备、提供者、项目和目标身份，排除冲突分配并核对最新事实；分配保存成功不是初始化成功，也不增加日常任务逐条审批。必要验证码及额外授权经受控协作处理，不放进普通说明输入框。

换机明确原手机、新手机、保留的同项目身份、原端停止情况、未决任务及新端条件；跨项目交接明确原/目标项目、资源、在途事实和收尾采集安排。运营确认后分别展示请求、实际停止、核清、分配及新端初始化结果，不能一次保存就显示全部迁移完成。

旧端失联、撤权或停止未知时保留待处理；不能让新旧两端同时接续执行。历史发布、效果、名额及连载关系保持原归属，未提交安排继续检查窗口和依赖，已提交/未知先核实。项目结束不自动释放资源，永久退出也不自动等于登录清理完成。

### 7.5 查看、申请、独占与交还

接管详情可从手机卡片、资源列表或原待办进入，固定显示设备、项目、目标发布身份、实际观察身份、当前操作方及关联任务。多处入口查看同一事项，不因进入页面新建重复待办。非手机问题直接补资料/处理决定，不强制先接管。

| 状态/动作 | 页面反馈与操作权限 | 后续判断 |
| --- | --- | --- |
| 仅查看 | 画面与时效、当前控制方；无法确认权限时只读 | 不自动认领或改变任务 |
| 申请接管 | 显示请求已受理、当前工作和等待停止确认 | 不能立刻启用手机点击 |
| 等待停止 | 同机 AI 操作在可确认节点停止，保留提交未知等事实 | 不凭请求超时或断线宣布取得控制 |
| 已取得独占控制 | 明确实际处理人、取得时间与范围，允许经验证的手机操作 | 所有同机 AI 界面操作暂停；其他手机按自身条件继续 |
| 他人控制中 | 显示实际控制者及最新情况，当前用户只读 | 内部同权不代表可同时或强行接管 |
| 提交处理结果 | 保存处理人、实际观察及完成/仍有问题/未完成等结果 | 不是交还，也不是恢复通过 |
| 交还请求 | 明确请求状态，冻结新的人工输入并等待实际控制确认 | 未确认交还不能启动 AI 操作 |
| 已确认交还 | 保留处理记录，展示恢复复核进度 | 根据当前页面与事实判断，不续点接管前下一步 |

处理记录和交还使用明确的独立动作。“交还手机”不以业务已经修好为前提；未解决也可交还并保留阻断，不能为必填长说明而困住控制。未保存说明提供保存草稿/保留输入等清晰选择，保存失败不能谎报已提交；具体 UI 不能把一个“完成”同时视为记录、交还、恢复。

同机互斥覆盖发布、手机采集、初始化、撤下以及人工接管，FB/YT 或不同任务类型不能分别持有控制。远程画面变旧、连接中断或设备撤权时立即停止允许新的人工操作，保留未知控制事实；重连先重新核对，不能自动重放先前点击。关闭浏览器、刷新、导航离开或服务重启不等于交还，返回依据实际状态展示，不靠页面计时器直接开放 AI 控制。

### 7.6 恢复复核与逐任务结果

人工处理提交且控制已明确交还后，在有效授权下核对设备当前连接、界面、发布身份、未决发布事实及原任务条件。没有手机操作的处理也要按实际影响复核；控制交还或人工说“已处理”都不直接将任务标为已恢复。

设备条件通过时，逐任务呈现：已发布核验保留原事实且不重发；尚未开始且条件有效的继续原安排或范围内重排；窗口已过或其他暂停仍有效的继续阻断；已提交或结果未知的先核实。任务可继续不等于立即执行或已发布，原有效排期和频率仍约束执行。

示例 SG-012/PUB-YT-004 的设计链路只说明：原第 3 集已核验、手机恢复后第 4 集仍检查原排期。历史大屏探索使用另一份归档真机资料，不将其设备、身份和失败回执套进 SG-012 的虚构成功链路。原“恢复成功”稿尚未制作，恢复行为以本节规格为准，不能用假记录凑成真实恢复证据。

R-150：正常端口变化及自动重连只更新设备状态和记录，不逐次外部提醒。恢复失败或需人工操作时进入对应待办：项目问题沿用负责人，分配前沿用 R-143；同项目同次故障更新原待办及影响范围，不因每次上报重复首次提醒。发送失败和未处理状态分别保留，连接恢复不批量关闭待办或解除设备暂停。

R-149：设备详情分别显示每台手机的当前配对会话、实际中心授权与连接核验结果；并发进展不汇成单个“全部配对成功”，一台异常不重置其他手机。运营只查看所需状态及非敏感失败原因，不展示提供者输入的系统配对码；原会话与迟到结果可追溯，同机竞争不静默另开。

R-148／R-151：受邀及归属核实后先开放仅用于核验的受限连接，节点绑定核验通过后自动批准正式网络准入；受限许可、正式策略应用及回收进度分别记录，不以 Tailscale 在线直接标为正式准入。运营端查看各层接入事实并处理关联不明或冲突的异常；分配前事项沿用 R-143，不新增逐台入网人工审批队列。首次项目与账号分配仍由运营确认，入网成功不能标为可执行业务。

提供者临时暂停立即停止新派发，停止确认与实际状态分开；提供者自行请求恢复后可在有效授权内进行必要检查，不需运营每次审批，也不授权新发布。提供者永久退出不等待运营批准才停派，远程清理仍须授权和连接，普通重连不能重新启用。恢复手机不能绕过项目/账号暂停或已失效权限。

### 7.7 验证与当前边界

本轮检查了 Demo 源码、历史截图/回执，并用 Playwright 打开本地 HTML 设计预览，核对原图加载、放大/关闭、焦点返回、未连接视图、禁用设备操作与两种桌面宽度。该检查仅是静态设计预览检查，记录见[检查结果](design/workbench/device-monitor-preview-check.json)，不替代仓库要求的实际 Web 入口业务验收。

当前检查未发现 3000/4318 端口监听，未自行启动服务，也未向手机发命令。实际真机大屏更新、截图时间对应、远程控制、多人互斥、失联后控制保留、提供者暂停期间停止手机访问、交还后的逐任务复核均尚未在新设计中验证。后续须从真实 Web 通过 Playwright 操作并核对实际回传，保留环境、脚本、断言与脱敏证据；既有远程执行按 R-109 复用其原覆盖证据，不重新宣称全部未验证。

## 8. 提供者与基础分佣

### 8.1 范围与入口

这是内部运营的辅助业务入口，不是提供者钱包或独立资金系统。页面帮助运营找到提供者及设备、核对账号承接与收益依据、跟进未决条件并保留处理记录。设计稿为[提供者详情](design/workbench/provider-detail-v1.png)与[收入及分佣依据](design/workbench/commission-detail-v1.png)，全部示例值不构成真实收益、默认比例或付款方案。

| 页面 | 首要字段与判断 | 主要动作 |
| --- | --- | --- |
| 提供者列表 | 标识、邀请/注册进展、关联设备及需处理事项 | 搜索、按进展筛选、进入详情 |
| 提供者详情 | 每台手机、项目及发布身份、独立准入/运行条件、收入记录摘要 | 查看设备、接入记录、账号承接历史和分佣依据 |
| 分佣记录列表 | 提供者、Page/频道、收益产生区间、原币种、收入及佣金/付款条件 | 按提供者/身份/条件筛选，进入原记录 |
| 收入与分佣依据详情 | 收入来源、到账、承接期间、适用比例、计算与处理事实 | 查看依据、查看比例配置、保存处理记录 |

详情返回保留来源列表筛选与位置。提供者姓名可能相同，记录使用明确业务标识；不根据同名自动合并收益或设备。未配置条件不阻塞设备接入和媒体主流程，只影响相关分佣计算与处理。

### 8.2 邀请、接入与多设备

首期由运营发放邀请，不开放无有效邀请的公众注册。按 R-152，创建表单支持配置成功注册次数上限及有效期，不要求预填受邀手机号；同一份邀请码与链接共用额度，用户验证自选号码即可注册，不再等待逐次审批。列表分别呈现有效／过期／撤销／名额耗尽、上限与已用／剩余名额、到期时间及实际注册进展，详情可追溯各成功注册提供者；首次使用后仍有名额时保持有效。生成、复制或打开链接不等于已发送或注册成功；撤销仅阻止后续注册，不取消已有身份或停止设备。运营可按需重新发放，后续新增设备不重复邀请。“查看接入记录”不会发送消息，具体发送通路及默认参数随实现落实；App 状态见[Android 规格](android-app-page-spec.md)。


每台手机显示独立的设备检查、运营分配、初始化、授权和运行条件；当前状态与所需操作分开。SG-012 等待恢复复核和 SG-021 提供者暂停可以同时存在，不把一位提供者标成整体故障或整体可用。进入“查看设备”返回第 7 节的同一设备/待办，不另建重复恢复流程。

提供者临时暂停、恢复请求及永久退出按 R-122/R-123/R-133 执行，不增加运营批准暂停或每次恢复的按钮。暂停/退出不新增扣罚，也不抹去历史承接和已核清收益。分佣页展示其影响，不在此直接改账号分配或替提供者恢复手机。

### 8.3 收入、归属与金额状态

2026-09-28 增补 R-144：临时暂停及技术掉线不结束原账号承接期间，不扣除这些时段的收益；仍按实际到账、核清归属及历史比例计佣。该规则以未永久退出或交接、承接关系仍有效为前提，不用设备在线时长代替承接记录；首次承接按 R-145 从对应账号初始化及真实发布身份核验通过、具备执行条件时开始，保留核验依据及生效时点，不追溯至分配、不等待首条任务，各账号分别核实；永久退出按 R-146 以系统受理并停止新派发的时点结束对应承接，保留原受理依据与终点，实际停止确认及清理分别展示；响应丢失查询不重置终点，未确认送达不能记作生效。

仅以关联 FB Page/YT 频道广告收益为分佣依据，引流收入不计入。按账号承接期间及收益产生区间核清归属，不按到账日、当前设备或最初发布内容的提供者重新分配；同账号换机或同提供者多设备不重复计佣。

| 事实 | 显示方式 | 不能推断为 |
| --- | --- | --- |
| 预估收益 | 来源、区间、币种、统计截止及预估标签 | 已到账或可结算佣金 |
| 已到账但归属未清 | 实际到账依据、来源收入总额、待核对原因 | 该提供者应得金额 |
| 已到账且核清归属 | 对应提供者、账号、承接期间和可归属收入 | 比例已配置或佣金已付 |
| 缺收益期间适用比例 | 未配置，佣金未计算 | 按 0% 或最新比例计算 |
| 收入与适用比例均明确 | 可结算佣金及其计算依据 | 已发生付款 |
| 没有可靠付款依据 | 暂无已核实付款记录/待核对 | 已付 0 或已付款 |
| 已有真实付款事实 | 金额、币种、时间、依据及处理人记录 | 平台收益或其他佣金也已付 |

上述是独立事实维度，不强制压为单一顺序状态。已核清部分与未核清部分分别呈现；不能为了展示总额把缺失、预估、到账和佣金相加。不同币种分别展示，不自动汇率换算；当前范围未选付款渠道，页面不承诺自动付款、提现或月度结算周期。

收益横跨承接或比例生效边界时，按证据支持的区间拆分；不能准确拆分则保持待核对，不按天数平均分配或用到账时间替代。后续补齐/更正关联原收入记录并保留前后依据，不复制成一笔新收入或重复结算。

### 8.4 比例与计算依据

比例为统一可配置值，具体值未确定，界面不得预填 10%、20% 等示例作为默认，也不新增按人议价。展示比例值、适用收益产生期间和配置依据，迟到账或未结算的旧收益仍匹配其产生期间生效比例，不用当前最新值追算。

在实际到账、归属及适用比例均已核清时，按对应区间的收入乘以适用比例计算，不另扣运营成本。界面可显示计算关系与原币种；金额精度、舍入及实际支付安排应在真实分佣处理前落实并验证，不在静态图中暗定。新配置或更正展示受影响记录和原依据，不静默改写已付事实。

“查看比例配置”进入配置说明与现有值，读取不修改。确需保存配置时，先展示拟定值、生效范围及影响；缺少必要值可保留筹备状态，不能标为已生效。此处不扩大成独立财务审批流。

### 8.5 处理记录及示例

示例 COM-009 对应林先生承接的 HomeVista，收益区间为 2026-08-01 00:00 至 09-01 00:00 UTC（结束不含），已到账且归属核清 USD 100.00；适用比例未配置，因此可结算佣金与实际已付均不能填入金额。手机 SG-021 当前暂停不自动扣减这一历史已核清收入。

COM-010 的 USD 240.00 是跨承接边界待拆分的来源收入，不能算为林先生全部应得；EST-011 的 USD 80.00 为另一期间的预估收益，不能并入可结算。示例中的月范围和美元只用于读图，不设固定结算频率或默认币种。

| 操作 | 反馈与限制 |
| --- | --- |
| 查看收入/承接依据 | 展示来源、实际区间及前后交接记录，不能用当前分配覆盖历史 |
| 查看待核对项 | 定位缺失/矛盾及影响，不自动拆分金额或选择收款人 |
| 保存处理记录 | 保存实际处理人、时间、说明及关联依据；提示“记录已保存” |
| 保存失败或并发变化 | 保留输入，显示最新事实及冲突，不静默覆盖别人更新 |
| 重复提交 | 关联同一次保存结果，不新增相同付款或收入事实 |
| 后续记录实际付款 | 必须对应真实金额、币种、时间和可靠依据；仅记说明不构成付款证明 |

处理记录不触发转账，也不能以“已处理”代替“已付”。收款渠道与支付方式尚未确定，当前稿不提供一键付款按钮；不收集无必要的银行敏感资料或将凭据写入普通备注。

### 8.6 异常与后续验证

空列表区分未接入提供者、已注册但无设备、无收入记录和筛选无结果；缺收入不写零收益。局部来源不可访问保留旧记录及其时效，并标该依据暂不可读取，不能无条件推翻或重新确认整笔收入。

后续 Playwright 应从真实 Web 查看提供者、进入设备与承接历史、下钻收入依据并保存实际处理记录，断言状态与关联保留；覆盖同名提供者、多设备去重、到账晚于交接、跨边界无法拆分、比例缺失、不同币种、重复保存和并发更新。真实付款结论另需实际依据，不能用静态金额或说明保存成功代替。当前仅有设计与文档核对，未进行支付、实收或 Web 业务验收。

## 9. 高影响操作与反馈

### 9.1 操作入口和一次明确确认

项目概览固定显示当前发布状态和相关操作入口：运行中可暂停；暂停后可按条件恢复；正式结束进入独立的影响确认页，不与暂停放在同一个含糊“停止”按钮下。运营同权，记录实际操作人，不能把项目负责人误当唯一可操作人。正式结束不要求先暂停；图稿从暂停进入仅是示例分支。

操作前展示明确的项目、影响范围、在途与未知事实、执行后仍会继续的工作，以及实际确认的动作。使用一次可审阅确认，不叠加通用“确定吗”、输入项目名或多重打勾来替代具体影响说明。查看影响不发指令，取消/返回不改变当前状态。以下规格是产品设计，并非本轮实际授权执行这些动作。

| 动作 | 操作前须可见 | 操作后分别呈现 |
| --- | --- | --- |
| 暂停项目发布 | 项目、受影响安排、已提交/未知事项；效果采集按条件继续 | 请求已受理、执行端停止确认、各任务实际事实 |
| 恢复项目 | 原暂停及仍有效的范围、素材、资源、窗口与依赖 | 检查中、可继续/重排、过期或仍阻断；不自动补发 |
| 正式结束项目 | 未提交取消范围、未决核实、收尾观察配置；资源不自动释放 | 停止请求、实际停止、取消记录、收尾与未决结果 |
| 撤回或更正素材 | 对象、版本及受影响任务，已提交/未知部分另列 | 实际保存/检查/取消结果；平台已有内容不自动改动 |
| 撤下平台内容 | 平台、Page/频道、内容、具体操作 | 已受理、执行及核验结果，未知先核实 |
| 提供者暂停/退出手机 | 显示提供者请求及其影响，不把它伪装成运营审批 | 停派发、旧端是否停止、授权和未决任务；重连不解除退出 |

确认采用具体业务摘要，按钮说明动作；只读查看、常规保存不堆叠确认弹窗。请求成功不使用“全部完成”等超出事实的反馈。

### 9.2 暂停发布：请求和实际停止分开

暂停确认摘要按事实分组：尚未开始、已进入编辑且可确认未提交、已提交/提交未知，以及已发布后续采集。影响量未取得时标未知，不能显示“0 项在途”；设备离线不能反推已经停止。必要时仍可提交停止新增的意图，页面说明在途停止尚需核实，不因读不到全部手机状态而伪称无风险或全部停妥。

按钮采用“确认暂停发布”，成功受理后进入[暂停进展稿](design/workbench/project-pause-v1.png)所示详情。分别展示操作记录、新发布启动限制的实际状态、执行端确认及每条任务的结果。仅已知受理时显示“请求已受理”；取得停止新增的事实后才能显示“已停止启动新发布”；仍有在途未确认时保留数量、对象与更新时间。

- 尚未开始：保留原安排和任务关联，不启动发布，不改成取消/失败。
- 编辑中且尚未提交：在可确认节点停止；停止请求与停止事实分别记录，失联时保留最后已知页面/时间及未知部分。
- 已提交或提交状态未知：继续核实原发布，不直接重发、删除或判失败；如果核实已发布，关联原任务并保留证据。
- 已发布效果：按既定安排继续尝试采集，但仍受授权、数据可用性、设备、提供者暂停和人工控制约束，不借采集启动发布。

暂停进展不是设备控制页，不提供强制断开手机、释放控制或“一键标记已停止”。需要人工处理时进入原关联待办或设备详情；停止尚在正常处理中只显示进展，不自动创建重复待办。真正异常按影响形成/合并原待办并保留具体任务状态。

### 9.3 恢复：按当前条件逐任务检查

恢复前展示原暂停、尚未停止确认/未决核实情况、有效范围、过期窗口及其他阻断。按钮采用“恢复并检查任务”，说明条件满足的任务可继续或在范围内重排，可能随后自动执行；不再要求恢复后逐条批准。

恢复请求受理后显示检查进度与最后更新时间。原在途状态、控制归属或提交事实未核清的任务不能重启；其他确实独立且条件有效的任务按批准范围继续。解除的是本次项目暂停，不能解除提供者暂停、账号限制、人工接管、撤权、素材撤回或其他有效阻断。

[恢复检查稿](design/workbench/project-resume-v1.png)分别显示项目暂停是否解除、每条检查结果及后续安排：检查中、可按原安排继续、允许范围内重排、窗口已过继续受阻、已提交/未知先核实。任务检查通过只是当时的可继续条件，执行前仍须核对最新事实；按排期待执行不等于已开始或已发布。

示例中的 PUB-FB-021 待原排期 11:00；PUB-YT-022 已确认未提交但 09:00–10:10 的窗口已过，不能补发；PUB-FB-023 提交结果未知继续核实。它们是 2026-09-28 的独立设计示例，不能与之前日期的图稿拼成真实记录。页面汇总随事实更新，不把“未提交”本身当作阻断原因，须说明具体未满足的条件。

### 9.4 正式结束：取消范围和收尾独立呈现

[结束确认稿](design/workbench/project-end-v1.png)在最终动作前展示：确认未提交且将取消的安排、仍需停止确认的编辑中任务、已提交/未知需继续核实的任务、收尾观察配置、资源保留和平台内容范围。图中任务清单是摘要，真实页面可展开全部对象，不能只显示前三条而暗中覆盖其他项目或内容。

结束不以设备已全部在线/停止为前提，但未知事实不能作为已停止或已取消结果。处理时再次核对最新状态，编辑中的先在可确认节点停止；确认未提交的剩余安排才取消。已提交或状态未知者继续核实，不能在项目结束时被普通批量取消覆盖。

收尾观察显示项目实际配置的期限、起算依据和预计结束时间，生效后保留实际起止记录。稿中“结束生效后 7 天”为示例设计，不是通用默认值。若配置尚缺或起算依据不明，明确“收尾配置待补/结束时间待确认”，不得自动填期限或显示收尾已完成；停止新发布的动作及实际进度仍可单独呈现，缺项交运营处理，不靠虚构值完成流程。

确认按钮“确认结束项目”对应结束发布与进入收尾，不隐含资源交接、退出登录、删除账号或撤下平台内容。成功受理后仍分别显示：停止新增、在途停止、逐任务取消/核实、收尾采集及报告。原已取消安排不能通过普通暂停恢复重新启用；若未来新增运营工作，须按当时批准与内容历史重新判断，当前不承诺“重开即补发”。

收尾按配置继续尝试取得历史已发布内容的数据；期限届满后汇总实际可得数据与缺失形成报告、停止常规采集。无法读取部分数据不延长为无限采集，也不能填零或强判成功；未决发布仍独立核实，不因收尾到期直接判成败。账号与设备保留原分配，另有明确交接操作才按第 7 节处理。

结束稿和恢复稿是可选择的两种路径，不是必须依次执行的流程。结束稿中的“保持暂停并返回”只适用于其当前暂停示例，运行中进入则显示“返回，保持当前状态”，不能在返回时附带暂停。

### 9.5 异步、并发和输入保护

| 场景 | 页面处理 | 禁止的误判 |
| --- | --- | --- |
| 点击后连接中断/超时 | 显示提交结果待确认，查询同一操作事实；保留说明 | 将网络错误直接视为未受理并重复创建动作 |
| 页面刷新或离开再返回 | 读回同一操作记录及各对象最新事实 | 仅凭新页面加载重新暂停、恢复或结束 |
| 审阅期间任务已提交 | 更新提交/未知分组和影响说明，执行以当前事实为准 | 按旧列表取消或重复发布 |
| 另一运营已暂停/结束 | 展示当前状态、实际操作人及原记录；过时动作失效 | 用旧“恢复”按钮重新启用已取消安排 |
| 部分设备未确认停止 | 新发布限制与各设备进度独立显示，保留未确认清单 | 以多数停止、断线或等待超时宣布全部停止 |
| 已填写说明未保存 | 保留草稿或明确放弃当前输入，失败不清空 | 普通说明保存替代高影响动作确认 |
| 新的相反控制意图 | 核对并保留前后操作关系，以当前有效意图检查各对象 | 迟到旧回执覆盖后来结束/暂停事实 |

高影响意图的更新不授予手机控制，不重置自动恢复额度、发布名额或连载进度。多人同权仍须按最新版本和实际控制处理，不扩展为管理员专属审批。

### 9.6 其他高影响动作与跨页面核对

素材撤回/更正沿用第 4 节，平台内容撤下沿用第 5 节，手机暂停/退出/接管及交接沿用第 7 节；这些动作以自身对象和范围确认，不能复用“结束项目”一次确认扩大权限。相关反馈采用同一原则：请求、实际执行、核验和业务结果分别呈现。

跨页面状态与返回规则集中见[跨页面流程核对表](workbench-flow-consistency.md)。后续 Playwright 须从真实项目入口打开影响摘要、执行获得授权的动作并断言实际状态，覆盖停止未确认、未知提交、窗口到期、部分恢复、重复提交、并发变更与结束收尾；真机相关证据由实际执行与回传支撑。当前图稿不证明任何项目被暂停、恢复或结束。

## 10. 通用状态与适配

### 10.1 同一事项的跨页面连续性

首页待办、项目概览、发布列表、任务详情和设备页引用同一任务与处理事实。进入其他页带上项目和对象上下文，返回恢复筛选、页码、滚动位置与合理焦点；受影响对象已不在原筛选时显示原因，不误称记录不存在，也不强行跳到另一条事项。

项目动作页可以保留操作发起时摘要，但须标明其时间/版本并与当前事实分开。页面事实尚未刷新时显示旧更新时间，不一边显示旧任务结果一边宣称已完成最新操作。全局队列重排不自动切换正在处理的对象，新紧急事项以可见提示出现。

待办已由他人处理或部分解决时，深链仍进入原记录并展示当前未决对象、历史处理与恢复条件；通知已读、人工说明已提交和手机已交还均不自动清除所有任务阻断。表单草稿保护独立于后台事实更新，不能为保留旧输入而回写旧状态。

### 10.2 共用状态和阅读适配

| 状态 | 页面表现与可继续动作 |
| --- | --- |
| 首次空状态 | 项目列表引导新建；项目内素材引导上传；已正常运行但无待办显示正常进展 |
| 筛选无结果 | 显示当前范围和清除筛选入口，不误称全局无数据 |
| 加载 | 保持页面结构；旧事实仍显示时标明正在刷新，不伪装为最新 |
| 局部失败 | 显示具体失败范围并保留成功结果、未保存输入；允许重试读取或保存，不等于重试发布 |
| 状态失效 | 展示最新事实及差异，要求重新核对受影响动作，不静默覆盖 |
| 数据陈旧或失联 | 明确最后更新时间与未知部分，保留仍允许的其他操作 |
| 操作不可用 | 说明阻断条件及处理入口；重要解释不能仅靠悬停 |

桌面首先保证普通笔记本窗口阅读和操作，再利用宽屏并列空间。首页双栏不以压缩正文为代价；较窄窗口可改为队列到详情的单栏浏览，并保持返回状态。具体断点待实际设计渲染验证。

手机浏览器仅阅读待办、详情与进展，复杂处理提示转电脑；不增加手机审批或接管。表格内容按阅读优先级组织，不把完整桌面表格缩小塞入手机。

键盘可进入筛选、列表与表单，焦点明确，进入详情或关闭浮层后返回合理位置；动态结果有可读反馈。颜色不能独立传递状态。上述为设计要求，静态图片不证明其实现。
