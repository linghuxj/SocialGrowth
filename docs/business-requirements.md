# SocialGrowth 业务需求与技术规划讨论记录

更新时间：2026-09-18。

本文记录讨论中的已确认需求、建议与待决定事项。前 3 个月系统架构与交付规格已在 [SocialGrowth 核心交付模块与内容规格规划书](delivery-specification.md) 中正式确定（涵盖 7 大核心模块）。

## 已确认需求

- 定位为面向 B 端企业的媒体运营自动化增长机制或系统，潜在服务对象包括 MCN 和有社媒账号增长需求的企业。
- 希望用 AI 承担运营规划、决策和内容发布，降低涨粉、交互与运营的人力和成本，为企业获取较准确的公域流量。
- 首期已有 AI 漫剧切片内容，通过分享切片获取社交媒体曝光，再将流量引导至漫剧平台。
- 漫剧切片需依据剧的类型或标签匹配不同账号。
- 账号需按地区、目标人群和垂直领域区分，不能无差别分发或运营。
- 用户提供的资源情况：前期约 100 台可正常使用的设备，优先覆盖 Facebook、Instagram、YouTube，约 300+ 个账号。这是可用资源规模，实际投入运营的账号数量将按处理能力逐步增加；已确认设备端自动化执行底座采用 **Google Artemis 纯真机移动设备池**（Samsung S23 等真实 Android 设备），**彻底排除模拟器**；单台真机设备在同一平台同一时期严格只登录 1 个账号，严禁同机切换多账号，封号后走冷备置换；目前假设所有设备在海外物理分散部署，暂时不考虑网络代理与文件传输问题（后续由其他基础设施解决）。
- 漫剧平台由甲方运营，目前本项目没有平台改造能力或用户行为数据接入权限。本阶段暂不考虑用户进入漫剧平台后的转化数据。
- 需要监控 Facebook、Instagram、YouTube 等社媒平台的表现数据（观看数、完播/时长、点赞、评论、分享、关注增长等），作为 AI 自动分析决策的主要因素。三平台的指标口径已在交付规格书（模块 7）中明确；**已确认采用双轨采集机制：若社媒官方 API 权限审核或限流无法达到要求，全面借助第三方数据服务获取相关统计数据**，确保数据采集与效果闭环不断裂。
- AI 分析之后，需要依据一定的规则和方案，经过一系列确认得到最终运营决策。前期由人员辅助确认 AI 分析和拟定的策略，具体审核流与自主托管开关已在交付规格书（模块 3）中明确。
- 最终决策由系统通过标准化 API/MCP 协议下发至 Google Artemis 调度服务，驱动真实移动设备（Samsung S23 等纯真机）在目标 App 上执行原生 UI 自动化分发、评论等动作，不走官方发布 API，并回传截屏与自愈日志。
- 分析或策略出现问题时，人员需要补充调整方案与规则描述，交由 AI 重新生成策略版本。
- 策略需要分批验证，首期已确定按 10%~20% 账号小批次试点、7~14 天观察窗口进行基线对照与一键安全回退（Rollback）。
- 长期目标是通过 AI 持续改进，最终实现分析、决策、分发和监控等完整流程的自主自动化；当前未确定具体学习机制，也未验证达到完全自主所需条件。
- 用户明确以观看量、流量转化、互动数等指标判断运营效果；三者在短链端与各社媒 API / 第三方数据服务的统计口径已在交付规格书中明确。
- 用户指定由平台提供导流短链，先统计再跳转至对应平台。已确认为 SocialGrowth 自建的核心服务模块（交付模块 4：导流短链服务），负责短链创建、302 跳转前事件记录、无效访问过滤（爬虫/预览识别）及分平台归因。统计采用短链端的数据，不要求改造甲方漫剧平台。
- 导流目的地由甲方提供，可以是对应平台的入口，也可以是某个指定页面；不要求所有短链都指向具体漫剧页面。
- 系统需要考虑内容生产能力：依据甲方提供的内容进行完善、调整与优化；甲方没有相关内容时，也可能需要由系统生成内容。剪辑、字幕、配音、封面等加工均属于可能需要覆盖的能力；**前 3 个月交付范围明确收敛于甲方已有成品切片管理与多维标签匹配分发，不涉及音视频剪辑渲染管线与视频生成**；**已确认独占式分发原则：确认内容绝对不重复，切片由人工确认后进行单独账号独占发送，系统级禁止跨账号重复分发，绝不出现同一切片出现在不同账号下**。
- 用户明确无素材生成以短视频为主要交付物，服务于社媒运营与引流。完整漫剧制作未被确认为当前交付要求；前 3 个月交付不包含视频生成。
- 日常使用和运营由公司专职运营人员承担。首期统一由一人辅助，以 AI 为主，暂不考虑人员分工。
- 前期根据实际处理情况逐步增加运营账号数量，不预设全部约 300+ 个账号同时投入运营。**已明确首阶段 3–5 台纯真机对应 6–10 个账号（Facebook 与 YouTube 各 3–5 个）**；**前期集中跑透 FB 与 YT 两个平台，待稳定后再加入 Instagram**；前 3 个月内平滑扩展至约 20 台真机（承载约 40 个账号）。
- 现有账号均为新申请账号，没有历史运营数据，需要覆盖起号与养号，并依据不同平台的规则和运营方式制定相应策略。
- 前期需要支持人员输入基于经验形成的运营方式和规则，作为 AI 拟定初始策略的基础；已规划经验规则引擎（模块 3.1），覆盖自然语言录入、结构化元数据、规则冲突检查与版本追溯。
- 已确认账号定位流程：运营人员输入甲方目标、内容资源和业务限制 → AI 提出各账号的地区、语言、人群与垂直方向 → 人工确认 → 根据实际表现提出调整建议。具体地区和题材在使用时配置。
- 设备端自动化执行底座确认为 **Google Artemis 纯真机移动设备池**（交付模块 6），包含守护调度服务与 Samsung S23 等真实移动设备池，**彻底排除模拟器**，通过标准化 API/MCP 协议接收策略指令并驱动目标 App 落实端到端原生 UI 自动化操作。
- 当前阶段暂不向甲方收费。未来收费方式与开始收费的条件尚未确定，不将暂不收费解释为长期免费。
- 用户明确未来一年全公司可用预算约 200 万元，当前仅规划技术相关预算与阶段交付；技术可分配额度尚未确定，当前按人民币理解。
- 已确认技术预算包含研发交付、上线后的技术运行和技术保障费用，覆盖技术人员全成本、开发及对接、AI 服务、基础设施、工具、测试运维与技术预备金。三人团队中的产品测试已按最新合并口径纳入技术预算，不另列运营工资；团队外运营工资、行政办公和商务费用归公司其他预算；设备采购维护及既有执行服务经常性费用归属待单独明确。
- 用户要求研发进度与预算测算体现 AI 时代的加速方式，不能直接沿用常规团队人数和工期。既有年度岗位、月份和费用假设不作为估算起点，需按交付成果及实际 AI 辅助研发能力重新拆解。
- 已确认以 4 周跑通最小运营闭环作为挑战目标，包含已有切片、经验规则、AI 策略、人工确认、Artemis 纯真机执行、短链统计及双轨社媒数据反馈。**Facebook 与 YouTube 两个平台分别跑通、分别验收**，Instagram 待稳定后再扩展。
- 首阶段试点数量已明确为 **3–5 台真机承载 Facebook 与 YouTube 各 3–5 个、合计 6–10 个初始投入账号**。已确立账号异常与风控管理机制（交付模块 5），覆盖封禁受限、分发限制提示、流量异常待分析与任务执行失败四类情况，自动暂停任务、触发冷备置换并保留完整证据链；持续可用数另行统计。

## 当前商业与成本边界

已确认当前暂不收费，收费模式留待后续讨论。建议将当前阶段重点放在完整运营流程、观看与互动及短链导流效果、单人辅助负荷和运行成本的验证上；阶段期限与验收门槛尚未确定。

建议成本统计覆盖 AI 分析、内容生成与加工、基础设施、存储和流量、设备运行及人工投入；预算应区分已有资源和新增支出。建议关联生产任务、运营账号与验证批次，以判断增加内容产量或账号数量的成本影响。

未来一年全公司可用预算约 200 万元已明确，本轮仅拆技术预算，已确认包含研发人力及上线后技术运行费用。下一步确认年度交付底线，再拆阶段与额度，暂不启动计费或支付功能建设。详见 [年度技术预算与阶段交付拆解](annual-plan.md)。原 180 万计划支出、20 万预备金和阶段费用表仅作为全公司测算历史参考，不作为当前技术预算基线。

## 首期运营方式与规模增长

已确认首期采用 AI 主导、一名公司专职运营人员辅助的模式，暂不规划多人分工与协作流程。甲方客户入口尚无已确认需求。

结合前述人工辅助流程，建议工作台集中呈现待确认策略、需要调整的内容或规则、正在验证的批次、执行异常及效果复盘。AI 承担分析和方案拟定，人员主要处理确认、纠正与异常；具体审核粒度仍需明确，上述功能布局尚未批准。

建议保留策略确认、规则修改、任务暂停等操作记录，以便复盘；不将多人权限和多级审批作为首期建设前提。

实际运营账号数量随处理能力缓慢增长。建议结合人工待办积压和日常投入时长、任务执行稳定性、内容供应能力、数据完整程度、效果表现及预算决定扩容，具体阈值尚未确定。

运营账号扩容与策略分批验证是两个不同维度：前者决定系统当前管理多少账号，后者决定某个策略先在哪些已投入运营的账号上验证。增加账号不自动扩大所有策略的执行范围。

## 账号定位流程（已确认）

1. 运营人员输入甲方目标、内容资源和业务限制。
2. AI 据此提出各账号的地区、语言、目标人群和垂直方向。
3. 人员确认账号定位，作为内容匹配及运营策略的依据。
4. 后续根据实际表现提出定位调整建议。

用户已确认上述流程；具体地区和题材无需在当前阶段固定。定位调整的生效与重新确认机制仍待细化，不将“提出调整建议”解释为 AI 已获准自动改变定位。

## 新账号冷启动与平台差异

已确认所有账号无历史运营，但前期可有人员提供既有经验规则。初始策略可以结合平台规则、人工经验与账号定位形成，不能假设已有本项目历史效果依据；地区、人群、题材等账号定位属于初始设定，后续实际受众特征需由可取得的数据验证。

建议将用户所说的起号与养号落实为账号资料与定位建设、功能及状态检查、首批内容测试、真实受众互动、持续内容优化和账号状态维护。具体操作尚未确认；不将固定浏览时长、机械点赞关注或固定等待天数写成已验证的增权规律。

建议按以下阶段组织业务，阶段条件和时间均待验证，不规定统一养号天数：

| 建议阶段 | 主要工作 | 下一阶段的判断依据 |
| --- | --- | --- |
| 初始化 | 明确账号类型、地区语言与垂直定位，完善资料，核实可用功能和导流入口 | 账号资料、内容准备、执行与数据采集条件 |
| 冷启动试验 | 依据初始定位提出内容假设，分批发布并观察反馈 | 数据完整性、足够的观察期和可比较的内容表现 |
| 持续运营 | 根据社媒与短链反馈调整内容、发布节奏和真实互动 | 效果、执行稳定性、人工负荷与成本 |
| 异常处理 | 识别功能限制、账号警告、执行或数据异常，按原因处理 | 原因与恢复条件；低观看量本身不能证明账号受到限制 |

建议分别管理平台官方规则、内部运营规则和待验证策略假设。每条规则记录来源、核验日期、适用平台与账号类型；AI 根据规则拟定策略，实验效果不能自动推翻平台约束。

人工经验导入为已确认需求，具体规则由运营人员在平台使用初期加入。规则录入与维护能力需在初期使用时可用，具体经验内容不作为当前需求整理的前置条件。建议允许人员先用自然语言描述方法，由 AI 整理为可检查的规则并交由人员确认，避免遗漏经验中的前提或将模糊描述直接下发执行。

建议规则库支持新增、修改、停用与版本追溯，并保留各版本参与的策略与验证结果。在尚未录入人工经验时，AI 只能引用已核实的平台规则、明确的业务目标和账号定位提出待验证方案，不能编造经验依据；该空规则场景的运行方式尚待确认。

建议每条经验记录来源与时间、适用平台和账号阶段、地区或受众、触发条件、操作内容、预期目标、例外情况及验证状态。规则是必须遵守的内部约束还是可以调整的经验建议，需要明确标记。

经验参与策略生成的建议流程：输入经验 → AI 结构化并检查与官方规则及其他规则的冲突 → 人工确认 → 形成初始策略 → 分批验证 → 保留、缩小适用范围、修订或停用。前期规则修订仍进入单人辅助确认流程，不因 AI 推断就自动改写已确认约束。

每次候选策略建议显示引用的经验、规则版本、调整原因和本次测试假设。未经验证的经验可作为初始依据，但不标记为已证实有效；局部验证成功也不直接推广到其他平台或人群。

已进行有限的官方资料核查，发现原创性和短链可点击位置直接影响本项目方案，详见 [平台规则核查记录](platform-rules.md)。这不代表三个平台的账号资格、自动化执行权限或所有操作已完成核验。

## 当前业务链路

内容与流量链路：甲方已有内容，或在缺少素材时由系统生成内容 → 按需要加工优化 → 描述内容类型、标签及适用受众 → 匹配账号定位 → 分发与运营 → 社交媒体曝光 → 用户访问导流短链 → 短链服务记录事件并返回跳转 → 甲方提供的平台入口或指定页面。实际到达目标页面仍不在当前可观测范围内。

前期运营决策链路：平台规则、人工经验、账号定位及可用数据 → AI 分析并拟定策略 → 人员辅助确认 → 形成最终运营决策 → 分批下发对应设备执行 → 收集执行、社媒表现与短链导流反馈 → 评估并调整下一轮策略。首次无运营数据时，以规则、经验和初始定位生成待验证方案。

调整分支：发现分析或策略问题 → 人员补充调整方案与规则描述 → AI 重新生成策略 → 返回确认流程。重新生成与再次确认的具体要求仍需细化。

本阶段效果优化依据为可取得的社媒表现数据与自有短链端导流统计，不能据此证明目标页面成功到达或进入漫剧平台后的观看、注册、付费与实际获客效果。设备执行是否成功与发布后的传播表现需分别处理，执行回执机制为待确认建议。

## 设备自动化执行子系统 (Google Artemis 纯真机)

已确认系统设备自动化执行底座采用 **Google Artemis**（交付模块 6），包含 Artemis 守护调度服务与真实移动设备池（Samsung S23 等真实 Android 真机），**彻底排除模拟器**。

所有设备假设已在海外物理分散部署，暂时不考虑网络代理与文件传输。SocialGrowth 核心中枢通过标准化 API/MCP 协议向 Artemis 调度服务下发策略指令；设备端驱动目标应用（Facebook App、Instagram App、YouTube App/Studio）完成端到端真实 UI 自动化动作，不走官方发布 API。单台真机在同一时期各平台 App 内仅登录 1 个账号，绝不同机多账号切换；封号后通过冷备账号置换上架。任务分发、回执与控制规格如下：

| 方向 | 覆盖的业务信息与执行规格 |
| --- | --- |
| 任务下发 | 任务标识、策略版本、验证批次、目标平台与账号、设备对应关系、目标应用包名、动作流（导航/点击/输入）、独占切片素材路径与文案、导流链接、执行时效要求 |
| 结果反馈 | 原任务标识、执行状态（待执行/已下发/执行中/已完成/失败）、实际执行时间、发布内容链接或标识、失败原因、截屏证据、动作坐标修正自愈日志（Self-healing Logs）与 Logcat 运行回执 |
| 任务控制 | 待执行任务的取消与暂停、过期任务处理、重复下发识别，以及异常状态下冷备账号置换与人工介入确认机制 |

设备执行结果（是否发布成功、回执证据）与发布后的社媒传播表现（观看量、互动率）分开独立处理。

## 渐进自主运营路径

系统按“人工辅助确认 → 小批次验证积累 → 策略级自主托管 → 完整流程自主”的演进路径推进：

| 演进阶段 | 运营与控制机制 | 验证与放开条件 |
| --- | --- | --- |
| 人工辅助确认 | AI 结合经验规则与定位拟定策略，运营人员在工作台逐条审核确认或驳回重生成 | 首月 30 个账号起步，跑通三平台真实运营闭环 |
| 分批验证与积累 | 策略采用 10%~20% 小批次试点、7~14 天观察窗口，通过基线组与实验组对照评估 | 具备可比较的样本数据，验证策略有效性 |
| 策略级自主托管 | 对已验证常规账号开启“自主托管开关”，自动生成并下发执行，异常时抛出人工告警 | 第 2 个月在 90 个账号规模下常态化运行 |
| 完整流程自主 | 在明确业务目标与平台规则边界内，全流程自动决策、分发、监控与安全回退 | 后续阶段结合更多业务线验证情况推进 |
