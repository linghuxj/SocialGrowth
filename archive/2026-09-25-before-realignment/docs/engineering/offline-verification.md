# 首条闭环：离线替身、数据样例与断言规格

版本：design-v1，2026-09-19。状态：测试设计及合成样例已提供，应用自动化测试待对应实现。用于 B-04 及两项未编号 QA 意见。实际发布仍走纯真机；离线构造载荷和回执不是 Android 模拟器，也不证明真实平台行为。

## 最小测试替身

替身位于 [执行契约](execution-contract.md)的网关与 Agent 边界，可为进程内函数或测试传输适配器，不要求新增常驻服务。正常单次测试应自行退出；禁止由 Agent 启动开发服务。

| 控制项 | 输入 | 输出/记录 |
| --- | --- | --- |
| 设备与绑定 | 纯样例 device/account/platform/binding 及 idle/busy/offline | Pull 请求；记录中枢实际下发对象，验证不借调其他账号设备 |
| 可控时间 | 固定当前时刻、计划/批准/挑战到期时间、推进时间动作 | 超时/过期事件；不靠真实等待十分钟测试，不另设生产时限 |
| 执行脚本 | 指定 task/attempt 的事件序列：提交前、处理中、人工挑战、已公开或明确拒绝 | 按契约返回回执，记录提交次数；默认不进行网络/ADB/文件删除操作 |
| 传输故障 | 丢弃、延迟、重复、乱序或断开回执 | 分别记录发出/收到的消息；可重传同 ID，不能等同重新提交内容 |
| 权限/数据变化 | 撤权、目标版本变化、目的地失效、共享设备故障 | 明确受影响、无法排除关联、确认无关联三组任务及核对依据 |
| 人工核对 | 操作人、证据引用、核对结果、当前授权/排期 | 记录人工恢复许可；仅验证码成功不得触发许可 |

测试必须能检查：任务/尝试记录、身份归属、首次发布事实、批准有效性、暂停范围、提交计数以及事件历史。检查“资源变 idle”不足以证明业务恢复。UI 提示不替代这些状态断言。

## 场景及可执行断言目标

这些是实现测试时必须落成的输入/输出，不是本轮已执行的应用测试。

| 用例 | 固定输入/注入事件 | 必须断言 |
| --- | --- | --- |
| T-01 专属路由 | 设备 A 绑账号 A、B 绑 B；A 忙/B 闲，队列任务属于 A | B 收到的 A 任务数为 0；A 任务仍等待，不跨号 |
| T-02 语言版本竞争 | 同身份字幕版/配音版，两个账号同时申请批准/归属 | 最多一个账号取得有效归属；另一方冲突；两个文件不是两份独立库存 |
| T-03 同账号重发 | 同身份已有公开历史，换语言/删除原帖后申请 | 新提交数为 0；首次已发时间/账号保留 |
| T-04 允许取消 | 所有版本确定未提交、无历史，旧批准及在途安排已失效 | 释放后无有效旧安排；新分配须重新审核，旧消息不能执行 |
| T-05 超时未知 | 已可能提交，丢回执，时钟越过技术超时并复位设备 | 结果 unknown，归属不释放，发布重试数为 0；设备资源恢复不解除业务暂停 |
| T-06 迟到公开证据 | T-05 后返回同尝试的公开 Post ID 和证据，再重复返回 | 补记一次发布；历史保留，合格发布计数只增加一次，不恢复旧计划 |
| T-07 明确未发布后恢复 | 明确拒绝证据且已排除处理中/公开；原账号权限有效，人工批准当前排期 | 新尝试引用旧尝试；旧失败记录保留；不得跨账号自动释放，无人工确认则提交数为 0 |
| T-08 影响范围 | 同设备 A 上 FB/YT；另一设备 B 已确认无同源权限/素材/入口/服务故障，批准有效 | A 上相关任务暂停，B 可继续；将 B 改为不能排除共同故障后，B 也须暂停 |
| T-09 挑战与排期到期 | 等待验证码期间排期过期，随后验证成功 | 旧任务不补发；验证事件保留，等待重排/批准，不自动恢复 |
| T-10 目标变化 | 同项目一条未开始、一条 unknown、一条 published | 未开始失效重审；unknown 核对；published 保留旧目标引用，不批量改写/重发 |
| T-11 退出与旧链接 | 项目退出，另有旧链接维护约定及 unknown 任务 | 停新增；按约定维护/停用原目的地，不自动改给其他客户；未知任务不释放 |
| T-12 非法消息 | 错设备、错账号、未知版本、同 ID 不同载荷、published 无证据 | 明确拒绝/待核查，无新的提交或错误事实覆盖；错误码与契约一致 |

T-08 的“确认无关联”不是简单的 ID 不同：样例中必须明确共同原因及设备/账号权限/素材权利/目的地/服务依赖，记录核对依据。缺少其中关键事实不能伪造无关联结论。实现可以采用关系查询加人工核对，不新增全局自动关联算法承诺。

## 指标可用性的合成金样

机器可读样例见 [metric-availability.json](fixtures/metric-availability.json)。所有 ID 和值均为合成测试数据，不证明 FB/YT 或供应商实际提供该字段。JSON 中的 `expected` 为测试期望，不是由应用得出的验收结果。

每个观察携带 `metricId/unit/scopeId/source/window/observedAt/availability/value/reason/evidenceRef`。可用性枚举为 `available/missing/delayed/unauthorized`；真实 0 使用 `available + value: 0`，其余不得补零。来源变化另外比较 source，不能用“有值”覆盖可比条件。

| 样例 | 内部逻辑期望 |
| --- | --- |
| F-01 有效零值 | 按真实零呈现，不能误标缺失 |
| F-02 缺失 | value 为 null 且显示缺失原因；必需主指标未完成 |
| F-03 延迟 | 保留延迟状态和观察窗；等待取证，不填零、不先宣布赢家 |
| F-04 无权限 | 与暂时延迟区别展示，保留责任/接入缺口；不得用公开评分替代主指标 |
| F-05 来源切换 | 即使有数值也先复核定义、范围和原比较资格；本样例明确尚未完成可比核查，不宣告改善 |
| F-06 合格试验无改善 | 必需执行、采集、评价完整但未满足原改善判据；闭环记录可完整，策略不标有效，不能自动扩大 |

对真实适配器另采集经许可、脱敏的供应商样本，记录指标定义、权限、粒度、时间窗、延迟及缺失映射；在此之前只验收合成数据规则，不把字段存在与供应商支持混为一谈。

## 分层验证记录

1. 文档/样例检查：JSON 可解析、状态/字段组合正确、编号与链接完整。本轮可以执行。
2. 应用单元/契约测试：实现按 T/F 场景构造输入并断言实际输出；未来执行时记录命令、结果和对应提交，不以样例文件存在代替通过。
3. 真实设备/供应商验证：确认真实通信、权限、UI 提交、回执证据和字段可用性；与第 2 层分别标记。
4. 业务验收：按既定批准、事实与 G-05 规则判断；替身成功不证明真实发布或商业效果。
